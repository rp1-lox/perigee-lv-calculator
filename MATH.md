# MATH.md — Rocket Playground Methodology

Every physics calculation in the program, where it lives, what it assumes, and where it's weak. **This file is load-bearing: if you change any math, update this file in the same commit** (CLAUDE.md enforces this). Critiques are collected at the bottom — add to them honestly when you spot a weakness; they are the to-do list for model quality.

Conventions: masses kg · thrust kN (converted to N internally) · Isp seconds · ΔV m/s unless noted · altitudes km above surface · `G0 = 9.80665 m/s²` · Earth `MU` (km³/s²) and `RE` (km) in `010-constants.js` · other bodies in `PROG_BODIES`. Every stage/engine carries ONE representative Isp — there is no altitude-dependent Isp anywhere in the program; users choose sea-level, vacuum, or trajectory-averaged values by convention (typically SL-ish for first stages, vacuum for uppers).

---

## 1. Rocket equation (the foundation)

`rocketEq(isp, m0, mf)` (140-physics.js) — Tsiolkovsky:

```
ΔV = g0 · Isp · ln(m0 / mf)
```

Degenerate inputs (mf ≤ 0, m0 ≤ mf) return 0. The program-side twins `progRocketEqDv(m_wet, m_prop_consumed, isp)` and its inverse `progRocketEqPropNeeded(m_wet, dv, isp) = m_wet·(1 − e^(−ΔV/(g0·Isp)))` live in 380 and drive mission burns.

Usable propellant everywhere excludes residuals: `prop_usable = prop · (1 − res/100)`.

## 2. Launch performance — the Townsend-Schilling model

`lvPerformance(stages, booster, pay, fairingMass, fairingJ, parkingAlt, onOrbitDV, siteLat, azMin, azMax)` (140-physics.js) is the single source of truth for ascent performance — the LV calculator, the mission LAUNCH event, the orbits-page vehicle selector, and every trade-study sweep all call it. It is an **empirical ΔV-budget model**, not a trajectory integrator: no altitude, drag, or pitch profile is simulated. Structure:

**2.1 Ideal ΔV per stage.** Serial stages burn bottom-up. For stage s with payload-above mass `spM[s]` (all stages above + payload + fairing while attached):

```
m0 = dry + prop_usable + spM[s],  mf = dry + spM[s]
ΔV_s = rocketEq(isp, m0, mf);   burn time bt_s = prop_usable / ṁ,  ṁ = F/(g0·Isp)
```

**2.2 Parallel boosters — event-driven integrator.** When booster groups exist, stage 0's ΔV/burn-time are replaced by a piecewise integration: between "events" (a group igniting at T-0 / after a predecessor / at a fixed time; a group or the core running dry) the active engine set is constant, so each interval is one rocket-equation step at the **blended effective Isp**:

```
Isp_eff = ΣF / (Σṁ · g0)        (true thrust-weighted harmonic mean, per interval)
```

Per-group `parallelMode`: `independent` (each burns its own tanks), `crossfeed` (boosters feed the core — the core reaches staging with full tanks; core mass-flow is drawn from the booster groups evenly), `throttle` (the core throttles to `coreThrottle` while that group burns — also reduces liftoff thrust). Spent groups drop their dry mass immediately. A guard caps the loop at 500 events. This block reduces exactly to the plain serial computation for a single ground-lit group (regression-tested).

**2.3 Gravity + drag losses (the empirical core).** With `Hp = parkingAlt` (km):

```
K3 = 429.9 + 1.602·Hp + 1.224e-3·Hp²         (m/s)
K4 = 2.328 − 9.687e-4·Hp                      (m/s per second)
T3s = 3·(1 − e^(−0.333·Vcirc/(g0·Isp_avg)))·g0·Isp_avg / A0
Tmix = 0.405·Ta + 0.595·T3s
ΔV_penalty = K3 + K4·Tmix
```

where `A0` = liftoff thrust / liftoff mass, `Isp_avg` = burn-time-weighted average Isp, and `Ta` = burn time **only up to reaching Vcirc** (fractional within the crossing stage via an exponential prop-fraction interpolation) — deliberately so low-thrust upper stages aren't charged gravity/drag losses for burns that happen after insertion. The K3/K4/T3s forms and the 0.405/0.595 mix are fitted constants from the Townsend/Schilling launch-performance estimation method; treat them as a package — do not tune individual constants without re-validating against known vehicles.

**2.4 Earth rotation credit.** `rotVel(lat, azMin, azMax)`: `V_rot = ωE·RE·cos(lat)·cos(az−90°)`, maximized over {azMin, azMax, 90°} and clamped to [0, ωE·RE·cos(lat)]. A site whose azimuth window excludes due east gets partial credit.

**2.5 The budget.**

```
DVasc = Vcirc + ΔV_penalty − V_rot
DVtot = DVasc + onOrbitDV
margin = ΣΔV_s − DVtot
```

**2.6 Max payload.** `lvMaxPayload(...)`: 40-iteration bisection on payload ∈ [0, 2,000,000 kg] for margin = 0 (margin is monotonically decreasing in payload, so bisection is valid). Returns 0 if even zero payload has negative margin.

## 3. Destination ΔV (`onOrbitDV`)

Two implementations that MUST agree: the original inside frozen `calculate()` (160) and the pure transcription `destOnOrbitDV(dest, siteLat)` (145) — pinned together by regression goldens captured from the real calculate() (tests/math.test.js). All burns are impulsive, all transfers two-body Earth.

**Orbit mode** (target apogee/perigee/inc from a circular parking orbit at `parkingAlt`), with `vPeri/vApo` from vis-viva:
- Target ≈ parking (both within 5 km): 0.
- Circular target (|apo−peri| < 5 km): Hohmann `dv1 = |v_peri(transfer) − Vc_park|`, then either
  - **combined plane change at apoapsis** if a plane change is needed AND apogee > 10,000 km: `√(va² + vc² − 2·va·vc·cosθ)` replacing the circularization burn (the classic GEO trick), or
  - separate circularization + plane change at parking-orbit speed: `2·Vc·sin(θ/2)`.
- Elliptical target: `dv1` raises apogee, `dv2 = |vApo(target) − vApo(transfer)|` adjusts perigee at apoapsis (skipped when |perigee − parkingAlt| < 50 km), plane change added separately (never combined).
- Plane change is only charged when `inc < |siteLat| − 0.5°` — the model assumes launch inclination = site latitude (minimum-inclination due-east launch) and that HIGHER-than-latitude inclinations are reachable by launch azimuth at no ΔV cost (the azimuth window only affects V_rot).

**Escape mode** (C3, declination): from vis-viva at the parking perigee,

```
V_inj = √(Vesc² + C3),  Vesc² = 2μ/r     →  onOrbitDV = V_inj − Vcirc(parking)
```

plus a declination plane-change penalty `2·Vc·sin(Δ/2·...)` when |siteLat| exceeds |declination| by > 0.5° (Δ = the excess). C3 below −Vesc² is rejected as an error.

## 4. Stage-and-a-half (S1.5)

`_s15BecoSplit(s)` (150). An S1.5 stage (Atlas-style: jettisonable booster engines + continuing sustainer) is split into two virtual serial phases before ANY physics:

- **BECO point** from a jettison-TWR criterion using **stage-only mass** (payload above is deliberately ignored; the comment claims < 5 % ΔV error for Atlas-class): `m_after = F_sust/(twr·g0)`; propellant before BECO is `prop_ph1 = (dry+prop) − (m_after + jet_mass)`.
- **Phase 1** (all engines): thrust = authored stage thrust; Isp = the authored stage Isp, OR — when the optional `s15_boost_isp` field is present — the **mass-flow blend** `Isp_ph1 = F_tot / ((F_tot−F_sust)/Isp_boost + F_sust/Isp_sust)`. Note the sustainer term reuses `s15_sust_isp` (stored as vacuum — see critique 10a).
- **Phase 2** (sustainer alone): thrust = `s15_sust_thrust`, Isp = `s15_sust_isp`, dry mass reduced by the jettisoned pack.

⚠️ The pure physics (`lvPerformance`/`lvMaxPayload`) knows nothing about s15 fields — every consumer must expand first. Splitters: `calculateWithS15` (worksheet), `_fleetExpandStages` (560), `_tsExpandStages` (165, also used by 167). This invariant has been violated twice; the gate has an Atlas golden guarding it.

## 5. Mission engine (program mode)

**Live stages** (370): a stage instance = dry mass + tanks (`fill`/`capacity` per propellant type). Burns drain tanks in order (`progBurnPropellant`); boiloff (`progBoiloff(fill, rate, days, insulation) = fill·e^(−rate·insulation·days)`, `progApplyStageBoiloff` applies it to every tank of a stage) is **ACTIVE (T2)**: `missionRecompute` calls it on EVERY live (non-EXPENDED/RECOVERED) vehicle's stages whenever the mission clock advances — COAST, the coast leg of a BURN (HOHMANN/TLI) or MANEUVER, and (negligibly) LAUNCH ascent time. Propellant type provenance matters here: LV stages get an Isp-inferred type from `progVehicleDefToLiveStages` (400) — always one of `LOX_LH2`/`LOX_CH4`/`LOX_RP1`, all of which have nonzero boiloff rates, so **LV stages DO boil off**. Spacecraft stages default to `propType: 'MMH/NTO'` (440) — NOT a key in `PROG_PROPELLANT_TYPES` — so an unedited spacecraft stage's tanks see `pt` resolve to `undefined` in `progApplyBoiloff` and **silently lose nothing**; only spacecraft stages whose propType is explicitly set to a `PROG_PROPELLANT_TYPES` key (e.g. `LOX_LH2`) boil off. This is a caveat, not a bug: unknown propellant = storable-by-default per critique 16f below.

**Boiloff ordering (T2)**: applied to ALL live vehicles at the point the clock advances, not just the acting one — so an idle depot boils off while another vehicle coasts/burns elsewhere. Per event type: LAUNCH — boiloff applied AFTER the ascent burn (order is immaterial; ascent is minutes, boiloff over that span is negligible — modeled but negligible, not skipped). BURN (HOHMANN/TLI) — boiloff applied AFTER the burn, for the coast LEG THAT BURN INITIATES (departure now, arrival later; matches the transit-corridor convention, critique 16e). MANEUVER — boiloff applied BEFORE the maneuver's own propellant burn, for the coast leg that PRECEDES it (the maneuver is the arrival burn ending that coast, e.g. LOI ending a TLC→LLO leg) — so a maneuver's burn draws from POST-boiloff tanks, meaning a coast that drains enough cryo propellant correctly starves the arrival burn and trips the existing burn-overdraw check (572 #2) with no separate check needed. COAST — boiloff applied for the coast's own authored `days`.

**Ascent staging** (`_missionApplyLaunch`, 570): the LAUNCH event runs `lvPerformance` on the snapshot vehicle (S1.5 expanded, boosters included in stage 0) to get `DVasc` (required) and per-stage ΔVs. It then walks stages bottom-up: stages whose full ΔV is consumed before meeting the requirement are burned dry and EXPENDED; the stage that crosses the requirement is the **insertion stage** — its propellant use comes from inverting the rocket equation on the full remaining stack (`progRocketEqPropNeeded` with mass-above included), leaving real residual propellant for later mission ΔV. Upper stages that never ignite ride to orbit untouched (there is deliberately NO forced stage-at-burnout). Spacecraft payload stages are never burned during ascent. When no performance data exists, the required ΔV falls back to `_missionDvToOrbit(body, alt) = Vcirc + fixed loss` with a per-body loss table (Earth 1550, Mars 1100, Venus 1700, Moon 20, Mercury 200, Titan 1400 m/s).

**Maneuvers** use the node-map physics (below) for required ΔV, then `progRocketEqDv/PropNeeded` against the active vehicle's stage stack. **Docking** requires `progOrbitalStateMatch`: same body, apogee/perigee within 1 km, inclination within 0.1°, LAN within 1°.

**Mission time (T1 — `missionRecompute`, 570)**: time is DERIVED from the replay, never authored as position. A mission clock (seconds) walks `m._expanded` in order; T-0 is the FIRST LAUNCH event (anything authored before it sits at T+0). Duration rules per event type:

| Event | Auto duration |
|---|---|
| LAUNCH | Ascent burn time — `lvPerformance`'s `tBT` (sum of per-stage burn times), cached onto `stagingResult.burnTime` |
| BURN (HOHMANN) | `progHohmannTOF(body, periBefore, burnParam)` — the Hohmann coast this burn initiates |
| BURN (TLI) | `progHohmannTOF('Earth', periBefore, PROG_MOON_ORBIT_R − R_Earth)` — the translunar coast |
| BURN (LOI) | 0 — arrival burn at the end of an already-counted TLI coast |
| BURN (CIRC / PLANE_CHANGE / CUSTOM) | 0 — treated as impulsive with no separate coast leg |
| MANEUVER | `progTransferTOF(fromNode, toNode)` — the coast, not the (impulsive) burn itself |
| COAST | `days × 86400` (authored — the ONLY event type where the user authors time directly; `durationOverride` is not applicable/needed here) |
| everything else (DEPLOY, SEPARATE, DOCK, EXPEND, RENDEZVOUS, transfers, REENTER, RECOVER) | 0 |

`progHohmannTOF(body, alt1_km, alt2_km)` = half-ellipse period `π·√(a³/μ)`, `a=(r1+r2)/2`. `progTransferTOF(fromNode, toNode)` classifies the node pair (mirrors `_nmDvPhysics`'s node shape): same-body circular/elliptic/surface → Hohmann half-ellipse between average altitudes; Earth → lunar transit/LLO/lunar-surface → translunar half-ellipse to `PROG_MOON_ORBIT_R`; Earth → interplanetary transit (Mars/Venus/…) → heliocentric Hohmann TOF via `PROG_HELIO_R`/`PROG_MU_SUN`, UNLESS the program has a selected Lambert launch window (`PROG_ACTIVE_PROGRAM.launchWindow.tof_days`), which is authoritative when present; anything else (surface↔surface, unmodeled pairs) → 0.

`PROG_HELIO_R` (360) now covers all eight planets (Mercury/Venus/Earth/Mars/Jupiter/Saturn/Uranus/Neptune — mean heliocentric radii, km), so `progTransferTOF`'s interplanetary branch transparently produces Hohmann TOFs for the outer planets too (previously only Mars/Venus were tabulated); critique 16c (no launch-window phasing) applies equally to these new entries — an Earth→Jupiter/Saturn/etc. TOF is a generic co-planar Hohmann estimate, not tied to an actual date. `PROG_MOON_ORBITS` (360) generalizes `PROG_MOON_ORBIT_R` into a small parent/radius map (`Moon` around Earth, `Titan` around Saturn at 1,221,900 km) for the Trajectory view's local-scene rings; it is not yet consumed by `progTransferTOF` (which still special-cases Earth↔Moon directly) — a future TOF generalization to arbitrary moon systems should read from this map instead of hand-adding cases.

**Overrides**: each log entry may carry `durationOverride` (seconds) and, for MANEUVER, `dvOverride` (m/s) — both authored fields that ride undo/autosave for free since they live on `m.log`. `durationOverride` replaces the auto duration in the clock accumulation. `dvOverride` replaces the node-map-computed ΔV requirement **before** propellant computation in `_missionApplyManeuver`, so the rocket equation (and everything downstream — flight-readiness checks, state-panel numbers) consumes the custom value consistently; there is no separate override-aware code path to keep in sync. Both are cached alongside the auto value (`e.durationAuto`/`e.durationUsed`, `e.dvAuto`/`e.dvRequired`) so the UI can badge overridden events "(custom)" and offer "reset to auto". `_metFmt(sec)` renders the running clock as `T+MM:SS` / `T+HH:MM` / `T+Nd HH:MM`; display only, never fed back into layout or physics.

## 6. Node-map ΔV physics (360 + 430)

`progNmComputeEdgeDv(from, to)` → `_nmDvPhysics`: same-body transfers compose Hohmann legs (`progDvHohmann`, vis-viva exact), plane changes (`progDvPlaneChange = 2v·sin(θ/2)`; `progDvPlaneChangeFull` gets the true angle between planes from the spherical law of cosines `cosθ = cos i1·cos i2 + sin i1·sin i2·cos ΔLAN`; `progDvCombined` vector-adds a plane change with a coplanar burn), and apoapsis circularization (GTO→GEO). Cross-body transfers are **patched conics with impulsive burns**:

- **TLI**: Hohmann from LEO to the Moon's orbital radius.
- **LOI/TEI**: v∞ at the Moon = |v_moon − v_apo(TLI)|, then hyperbolic-to-circular at LLO: `ΔV = √(v∞² + 2μM/r) − √(μM/r)` (the Oberth form). TEI is assumed symmetric to LOI. The code itself documents the known underestimate (~822 m/s vs ~900 real Apollo LOI with free-return constraints).
- **TMI/TVI + MOI/VOI**: heliocentric circular-coplanar Hohmann between planet orbits gives v∞ at departure/arrival; departure and capture burns use the same Oberth form at LEO/target-orbit radius. No plane change, no synodic timing (timing lives in the porkchop, separately).
- **Surface↔orbit**: Earth ascent uses the launch model; lunar/Mars ascent are scaled baselines (`1870 m/s` at LLO-100, `3810 m/s` at MCO-400, scaled by the ratio of target-orbit circular speeds). Descent numbers mirror ascent.

## 7. Porkchop plotter (410)

A real **Lambert solver** (universal variables with Stumpff functions C(ψ), S(ψ), bisection on ψ) over a departure-date × time-of-flight grid, on a **circular, coplanar** planet model (fixed radii, periods; phase angle `theta0` calibrated so the Hohmann window sits near T+0 — dates are therefore RELATIVE, not calendar). Output: C3 heatmap; the selected cell sets the program's launch window / coast duration. Independent of the node-map ΔV numbers.

**Now user-facing** (previously dormant machinery with no UI entry point). Mars/Venus only — the only two destinations with tuned `PROG_PORK_DATA`/`PROG_BODY_KINEMATICS` calibration; other transit destinations show a greyed "⚟ Launch window…" button with a tooltip instead. Entry points: the Add-Event MANEUVER form and the event edit modal, both on interplanetary legs (`toNode.orbit.type==='transit' && orbit.body==='Sun'`); a chip on maneuver cards shows the active window or "Hohmann default" and reopens the modal. The modal (`modal-mission-porkchop`, 570/410) renders the C3 heatmap onto a `<canvas>` (`progPorkRenderCanvas`, one pixel per grid cell, `image-rendering:pixelated`) with a live hover readout and click-to-stage selection; Apply commits the pending selection and calls `missionRecompute`. The heatmap's blue→red C3 ramp is a fixed perceptual gradient used as **data**, exempt from the chrome theming rules (`progPorkC3Color`) — canvas chrome/labels (axis captions, buttons) use `var(--…)` as usual.

`launchWindow` shape: `{ destination, dep_day, tof_days, c3 }` (`PROG_PORK_DESTINATIONS = ['Mars','Venus']`), stored on `PROG_ACTIVE_PROGRAM.launchWindow` and destination-keyed so a Mars window never affects a Venus leg — both `progTransferTOF` (360) and any leg-timing consumer check `lw.destination === dest` before using it. It rides `buildProgramObject()`/autosave for free since `PROG_ACTIVE_PROGRAM` is bundled wholesale (450/455) — no separate persistence path needed.

**Precedence** (highest wins): explicit per-event `durationOverride` (authored on the log entry) > selected `launchWindow` for that destination > generic Hohmann TOF estimate. Implemented once, in `progTransferTOF` (feeds `durationAuto`) and the mission replay's `durationUsed = overrideSec != null ? overrideSec : durationAuto` (570) — the window is just one of the two inputs to `durationAuto`, so no separate override-vs-window branch was needed.

C3 calibration (574 `_trajGetPlanetCalibration`/`progCalibratedTheta0`, 360) needed **no direct launchWindow branch**: it calibrates a destination planet's `theta0` from the leg's actual replayed `met`/`metArrive`, which already reflect the window's `tof_days` via `progTransferTOF` above — the trajectory arc closes by construction once the window changes the leg's `durationUsed` and downstream MET.

## 7a. Body kinematics (C1a)

`PROG_BODY_KINEMATICS` (360) is the single source of truth for every body's orbital period and phase angle, feeding both the trajectory view (574) and the porkchop plotter's `PROG_PORK_DATA` (410). Model: **circular, coplanar, uniform angular motion** — `progBodyAngleAt(body, t_s) = theta0_rad + 2π·t_s/period_s`, normalized to `[0, 2π)`. `progBodyWorldPos(body, t_s)` returns a heliocentric `{x,y}` km point: the Sun at the origin, planets on their `PROG_HELIO_R` ring at their current angle, and moons as `parent position + moon-ring offset at the moon's own angle` (recursive on the parent's position, so a moon's world position also moves with its planet).

Periods are stored **canonically in seconds** (`period_s`, computed from published day values) specifically to eliminate the seconds-vs-days unit-conversion bug class at the source — every consumer works in seconds, no per-callsite `×86400` or `/86400`.

**θ0 calibration story**: Earth/Mars/Venus `theta0_rad` are NOT independently chosen — they are read directly from the porkchop plotter's pre-existing calibration (`PROG_PORK_DATA`, 410), which was tuned so a Hohmann departure window lands near day 0. All other bodies (Mercury, Jupiter, Saturn, Uranus, Neptune, Moon, Titan) use the schematic spread angles the trajectory view (574) already drew before this change (`(i/8)·2π − π/2` for the 8 `PROG_HELIO_R` planets in their declared key order; `0` for Moon/Titan, matching their prior fixed body-scene ring angle) — extracted verbatim so a t=0 render is pixel-identical to the pre-C1a static scene. The absolute rotation of the whole body set is arbitrary (only the phase DIFFERENCES between planets matter physically); this is why the porkchop's calibrated values could be adopted as-is for Earth/Mars/Venus without needing to re-rotate the other five bodies — verified in-browser that the Sun scene at t=0 (empty mission) is unchanged and the porkchop's Mars−Earth / Venus−Earth phase differences are numerically identical to their pre-unification hardcoded values.

**View-time rule**: the trajectory view's `_trajViewTime(m)` (574) picks the time used to place body glyphs — mirroring the mission state panel's "state AS OF this event" semantics exactly (`_missionSelectedEventSnapshotEntry`, 570): if an event is selected, `metStart + durationUsed` of that event (its POST-event time); otherwise the mission's total elapsed time (`m._metTotal`); otherwise `0`. NaN/undefined inputs are guarded to `0`.

**Per-mission planet-phase calibration**: with `theta0` fixed per the table, a true-shape Hohmann arc between two heliocentric rings only visually connects (its arrival endpoint lands exactly on the destination planet) when the phase angle between departure and destination body at `t_dep` happens to equal the Hohmann geometry's required 180°-apart-at-arrival relationship — at an arbitrary mission MET it generally won't. `progCalibratedTheta0(destBody, t_dep_s, t_arr_s, departBody)` (360, pure) computes the ADDITIVE theta0 offset that makes it satisfy that relationship for one specific leg:

```
requiredArrivalAngle = progBodyAngleAt(departBody, t_dep) + π
tableArrivalAngle    = theta0_table(destBody) + 2π·t_arr/period(destBody)
offset                = requiredArrivalAngle − tableArrivalAngle
```

Rule set, applied by the trajectory view's render pass only (574, `_trajGetPlanetCalibration`):
1. A mission's **FIRST** Sun-departed transit leg (`fromO.body === 'Sun'`) to a given heliocentric destination planet calibrates that planet's theta0 **for this mission's render only** — the offset is computed once and cached per-mission (`_trajCalibrationCache`), never written into the global `PROG_BODY_KINEMATICS` table and never persisted to `m.log`/autosave. Legs are considered in mission-authored order (`leg.authIdx`) across ALL body frames — a real interplanetary transit leg is extracted into the DESTINATION planet's own local frame by `_trajFrameForOrbit` (not literally a `'Sun'` frameId; only the impulsive corridor-injection leg, which has no usable TOF since `met === metArrive` by the transit-corridor convention, lands in a `'Sun'`-ish frameId), so the scan walks every frame's legs and filters on `fromO.body === 'Sun'` directly rather than assuming a single `'Sun'` frame holds them.
2. **Porkchop launch-window override**: `progTransferTOF` (360) already applies `PROG_ACTIVE_PROGRAM.launchWindow.tof_days` as an override on `durationUsed` for the affected leg (same `lw.destination === dest || !lw.destination` matching used elsewhere) — since `progCalibratedTheta0` is fed the leg's actual `met`/`metArrive` (which already reflect that override), a porkchop-selected window's timing flows into the calibration automatically. **No separate code path was needed** — verified by tracing `progTransferTOF` (the leg's `durationUsed` already equals `window.tof_days × 86400` when a window is active) and confirming `progCalibratedTheta0` has no independent TOF computation of its own.
3. A **SECOND** leg to the same destination planet within a mission cannot also be satisfied (only the first gets to calibrate) — it renders schematic ghost endpoints (dashed-outline circles, matching the C2 Moon-lead ghost-marker styling) at its own departure/arrival points joined by a faint dotted line, instead of a connecting arc. Hover title: `"phase not shown — planet position calibrated to the first <body> transfer"`. Implemented in both places a Sun-departed leg's geometry is drawn: the heliocentric (`isSun`) branch of `_trajBodyFrameContent` (574) and the local-destination-frame branch (the actual leg with real TOF, per the frame-routing note above).
4. Planets that never receive a calibrating leg keep table theta0s untouched (absent from the overrides map, offset 0) — the pre-existing render path is already correct for them. The **Moon is untouched**: calibration only fires for bodies in `PROG_HELIO_R` (heliocentric planets), explicitly excluding anything in `PROG_MOON_ORBITS` — Earth is also never a calibration target (home base, never a "destination").
5. Footer note **"planet phases calibrated to mission transfers"** appears only when at least one calibration is active for the current mission's render pass (`_trajGetPlanetCalibration(m).active`).

Rendering integration: `progBodyWorldPosCalibrated(body, t_s, overrides)` (360, pure, additive to `progBodyAngleAt`'s existing angle — does NOT modify `progBodyWorldPos`'s signature or behavior) mirrors `progBodyWorldPos`'s moon-recursion but adds `overrides[body] || 0` to a heliocentric planet's own angle before computing `{x,y}`; a moon's own angle is unaffected, but its PARENT position input flows through the same calibrated recursion, so a calibrated planet's moons move WITH it. `overrides` (`{bodyName: offsetRadians}`) is threaded through every consumer of a heliocentric body's position in `_trajWorldSVG`'s render pass — the planet ring/glyph/ZOI-content anchor, the moon-ring parent-position lookup, and the camera's own floating-origin center (`_trajCamCenterKm`, extended with an optional `overrides` param) — so glyph position, embedded-content anchor, and camera anchor are always coherent (verified in-browser: identical `{x,y}` from the same `progBodyWorldPosCalibrated` call feeding both the glyph and the ZOI content anchor).

**Bug found and fixed while implementing this**: `_trajFrameForOrbit` (574) checked a field `o.transit` that is never actually set on any node-map orbit spec — the real field is `o.type === 'transit'` (see `PROG_NM_NODES`, 430, e.g. `mars-transfer`'s orbit is `{type:'transit', body:'Sun', destination:'Mars'}`). This silently made every Sun-frame/translunar-frame routing decision in that function fall through to the plain `o.body` branch — harmless for `body:'Sun'` transit nodes (same result either way) but meant the function's SPECIFIC transit-vs-plain distinction was unreliable for any caller depending on it, which the planet-calibration scan does. Fixed to check `o.type === 'transit'`.

## 7b. Trajectory view LOD ramps + mission-state rendering (C2)

**LOD opacity windows**: `_trajLodOpacity(sizePx, lo, hi)` (574) replaces C1b's hard visibility culls with a linear fade — 0 below `lo`, 1 through the middle of the window, a ramp back to 0 approaching `hi` (finite windows only). Ramp width is `min((hi-lo)*0.2, lo*0.2)` — capped at 20% of `lo` itself, not 20% of the full span, because every window in this app pairs a small `lo` (8-30px) with a huge `hi` (15x the viewport diagonal, i.e. "effectively never fades back out") — an uncapped 20%-of-span ramp would be thousands of px wide and make anything just past `lo` read as nearly invisible. `hi = Infinity` (or any non-finite/≤lo value) selects "fade in only, no ceiling" mode, used by the zone-of-influence window. Windows (feature: `[lo px, hi multiplier of viewport diagonal]`): heliocentric planet ring `[8, 15x]`; moon ring `[10, 15x]` (inherited from parent, see below — not applied standalone); mission orbit ring `[12, 15x]`; transfer arc `[10, 15x]`; zone-of-influence `[30, ∞]` (fade-in only). Body discs keep their pre-existing min-px clamp + true-scale rule with NO fade (a body is always at least visible).

**One fade authority per feature**: a moon's ring and a body's embedded mission content (its own moons + mission orbit rings/arcs) do NOT apply their own LOD window on top of their parent's — they inherit the parent body's zone-of-influence alpha (`parentZoiAlpha` / `zoiAlpha` in `_trajWorldSVG`) as a single multiplicative wrapper `<g opacity="...">`. A ring's own window (`missionOrbitRing`, `transferArc`) governs ONLY that feature's fade within an already-visible zone — it is never multiplied against the parent's zone alpha a second time.

**Far representation** (fixes the C1b zoom-out handoff): a planet's disc never fades (unchanged true-scale/min-clamp rule), but its NAME label is force-eligible — bypasses the normal screenSize/minSize gate — whenever `trueR * zoom < _TRAJ_MIN_BODY_PX`, i.e. whenever the disc itself has hit its min-px clamp (we're zoomed out far enough relative to THAT body that it's rendered as glyph+name rather than a legible true-scale disc). This is evaluated per-body, not tied to the ring's own visibility window, specifically because the 8 heliocentric rings span wildly different radii (Mercury's ring is tiny next to Neptune's) — at full solar zoom-out every body is equally "far" even though its ring's own LOD alpha may already be 0. Overlay symbology (labels/markers) inherits its parent feature's resolved alpha via a `opacity` field threaded through `_trajRegisterLabel`/`_trajResolveLabels` — a label still needs BOTH its feature's alpha > 0 AND its own size/collision gate to render.

**Corridor state rings are gone**: `_trajCorridorMoon` (a peri≈LEO / apo≈moon-orbital-radius snapshot detector) now SUPPRESSES ring generation entirely at the extraction layer (`addOrbitRing` returns `null` for a corridor-shaped snapshot) rather than relabeling it "TLC corridor" — transfer arcs carry all transit meaning now, so a mid-coast vehicle snapshot no longer draws a redundant giant ellipse ring alongside its arc.

**Moon-lead arc orientation**: `_trajArcRotationForTarget(ox, oy, targetX, targetY)` (pure) solves the transfer-arc rotation so its arrival endpoint lands on a specific target point rather than a fixed schematic angle. Derivation: `_trajTransferArcPath`'s arrival endpoint (local `(-rApo·scale, 0)`, since periapsis is fixed at local angle 0) lands at screen angle `180° + rotDeg` after rotation, so `rotDeg = atan2(dy,dx)·180/π − 180` (normalized to `(-180°,180°]`) makes it land on `(targetX,targetY)`. Applied at two sites: (a) the Sun-frame interplanetary case, target = `progBodyWorldPos(destBody, t_arrive)` where `t_arrive = leg.metArrive` (or current viewTime if the leg has no recorded arrival); (b) the local-moon case (e.g. Earth-frame TLC arriving at the Moon — though see the Moon-frame patched-conic note below for how this leg actually gets drawn), target = `progBodyAngleAt(destMoon, t_arrive)` projected onto the moon's ring. A dim dashed-outline **ghost marker** (`_trajGhostMarker`) is drawn at the arrival-time position, LOD-gated and labeled "`<body>` at arrival", ONLY when that position differs from the body's current-viewTime position by more than 3px on screen — otherwise the Moon hasn't visibly moved and the marker would just be clutter.

**Patched-conic seam in the destination's own frame** (`_trajLocalRadius`, C2 fix, then C2-review fix): a transit leg whose `destination` field equals the FRAME body itself (e.g. rendering the Moon frame, and the leg's `fromO` is `{type:'transit', destination:'Moon'}`) has no finite body-centered departure radius — the true departure point is a hyperbolic approach relative to the Moon, which this app doesn't model (patched-conic ΔV only, §6). Previously this made `_trajLocalRadius` return `null` for the departure end, so the leg's arc silently never rendered AT ALL in the destination's own frame (only the parent-frame stub burn-marker showed) — the actual TLC coast arc with its vehicle dot was invisible. Fix: a schematic fallback returns a finite "SOI edge" departure point, giving the arc a finite (if arbitrary) starting radius to draw from. **Follow-up fix (C2 acceptance review):** the fallback originally used `20 × the destination body's OWN radius` (~34,748 km for the Moon) — a value with no relationship to the actual departure-arrival gap. Because every LOD gate in this file is evaluated in real screen px (one-fade-authority rule, above), that made the leg's visibility a function of camera zoom alone: at Moon anchor the camera is zoomed in tight enough that even this tiny schematic radius reads as a large on-screen arc past the `transferArc` window's 10px floor; at Earth anchor (zoomed out to frame the whole Earth-Moon gap) the SAME arc's drawn extent collapsed under that floor and the leg silently vanished — even though the mirror leg in the parent (Earth) frame, which correctly uses the moon's full ORBITAL radius (`mo.r`) as its far endpoint, rendered fine at the same zoom. Fixed by scaling the SOI-fallback radius off `mo.r` instead (`max(2×bodyR, 0.5×mo.r)`; ~192,200 km for the Moon) so both ends of the cross-frame leg agree on the physical scale of the gap they schematically bridge, and the arc's drawn extent clears the `transferArc` LOD window's px floor with headroom at typical Earth-fit zoom (verified in-browser: ~19px vs. the 10px floor, up from ~4px pre-fix). Not a physical Hill-sphere/SOI calculation — the real value is picked purely to keep the arc's on-screen size consistent and above the LOD floor across camera anchors, not to model the true hyperbolic approach geometry (the Moon's actual Hill sphere is far smaller, ~60,000 km ≈ 0.156×mo.r).

**Mission-state trimming**: each transfer leg is classified relative to the current `viewTime` (`vt`) using its `met`/`metArrive` (both required — a zero-duration/impulsive leg, e.g. an injection burn with `met === metArrive`, always renders "planned" since it has no coast to trim): **history** (`metArrive <= vt`, dimmed to `_TRAJ_HISTORY_ALPHA = 0.35`, solid stroke) — the leg has fully completed; **current** (`met <= vt < metArrive`, full strength, solid stroke, PLUS a schematic vehicle dot) — the leg spans the current viewTime; **planned** (`met > vt`, today's dashed rendering, unchanged) — not yet departed. Orbit rings get the same history treatment when ALL their owning vehicles have a recorded vehicle-level `EXPEND` at or before `vt` (`expendMetByOwner`, keyed by `_originKey` — stage-level EXPENDs don't retire a whole vehicle so are intentionally not tracked here; a multi-owner co-located ring with even one surviving owner stays current).

**Vehicle position (schematic, NOT Kepler)**: for a "current" leg, `_trajLegPathFraction(metDepart, tof, viewT) = clamp((viewT-metDepart)/tof, 0, 1)` gives a LINEAR path-length fraction, and `_trajArcPointAt(r1,r2,scale,rotDeg,ox,oy,t)` walks the SAME half-ellipse `_trajTransferArcPath` draws (parametrized by `theta = t·π` sweeping periapsis→apoapsis) to place a dot exactly on the rendered path. **Critique**: this is uniform PATH-LENGTH-ANGLE progress, not true orbital motion — a real vehicle moves faster near periapsis (Kepler's second law / true anomaly rate is non-uniform), so the dot's on-screen speed is constant while a real vehicle's isn't. Acceptable for a schematic "where roughly is it" indicator; not a claim about real transit speed at any point along the arc.

## 7c. Physics core P0 — two-body machinery (385)

Foundation layer for the n-body plan (PHYSICS_PLAN.md); **not yet consumed by any mission math** — P0 adds capability, changes no behavior. All 3D-native (`[x,y,z]` arrays; the program passes z = 0 until the P5 camera).

- **Elements ⇄ state** (`physElementsToState` / `physStateToElements`): classical set {a, e, i, Ω, ω, ν}, perifocal→inertial rotation R3(−Ω)R1(−i)R3(−ω). a < 0 hyperbolic. Degeneracies pinned explicitly: e ≈ 0 → ω := 0, ν measured from node (or +x if equatorial); i ≈ 0 → Ω := 0, ω = longitude of periapsis. Threshold 1e-10.
- **Universal-variable propagation** (`physKeplerPropagate`): Curtis Alg. 3.4 — Newton on χ with Stumpff C/S (single copy, moved from 410; the Lambert solver consumes the same functions), then f/g and ḟ/ġ. One code path for ellipse/parabola/hyperbola; returns null on non-convergence (80-iteration cap) rather than a wrong state.
- **Body rails states** (`physBodyStateAt`): position through `progBodyWorldPosCalibrated` — the ONE body-position source (calibration coherence invariant) — velocity analytic for circular rails (v = ωr, tangential), recursive for moons (parent + local).
- **Pinned in the gate**: round-trips to 1e-9 across LEO/GTO/Molniya-like/inclined/hyperbolic; energy and |h| invariance along propagation; full-period return to start; half-ellipse arrival time consistent with `progHohmannTOF`; Moon rail speed ≈ 1.018 km/s, Earth ≈ 29.78 km/s, rails tangential.

## 7d. Physics integrator P1 — restricted n-body propagation (386)

Vessels are massless test particles; bodies ride analytic rails (`physBodyStateAt`, §7c). **Not yet consumed by mission math** (P2 wires it in). Model:

- **Frame policy**: integration happens in the vessel's dominant body's frame (its SOI), with perturbers in the standard relative-motion form — direct minus indirect tidal terms, `μ_p[(d−r)/|d−r|³ − d/|d|³]`. With one perturber this IS the restricted three-body problem in relative coordinates; it also keeps coordinates small near the body that matters.
- **SOI model**: `r_SOI = a·(μ/μ_parent)^(2/5)` (Moon ≈ 66,183 km, Earth ≈ 9.25e5 km, pinned in gate). Frame handoffs (`physPatchState`) convert position AND velocity through the shared rails; transitions are detected per-step and recorded as events.
- **Integrator**: leapfrog (kick-drift-kick), 2nd-order symplectic — energy error oscillates instead of drifting (measured ~1e-14 relative over 100 LEO orbits). Step size = local circular-orbit timescale / 360, quantized DOWN onto a fixed power-of-4 ladder (1…65,536 s) — quantization is what makes runs **bit-for-bit deterministic** (replay/undo/golden safety).
- **Events**: apsides via r·v sign change; SOI crossings; `physFindEventTime` bisection available for precise event location.
- **Single entry point**: ALL propagation goes through `physPropagateSegment` (hard invariant — no ad-hoc integrators). Sample polylines decimated to ≤ maxSamples with endpoints/frame-changes preserved.
- **Measured fidelity (2026-07-09 tuning run)**: two-body phase error ~0.3 km/orbit at LEO (vs analytic Kepler); Jacobi constant on a violent e=0.95 lunar-grazing orbit drifts ≤ 7.7e-4 relative over 15 days; a scanned free-return seed (185 km LEO, apogee 455,000 km, burn angle 4.5379 rad) transits the Moon's SOI and returns to a 62 km Earth perigee — pinned as the golden.

## 7e. Physics mission bridge P2 — solved node burns (565 + 570 hooks)

First phase where the physics stack is CONSUMED by the mission model. `PHYS_ENABLED` (565, const, true) gates everything; results live in the module side-table `_physTrajByMission[missionId] = {legs}` — never on the mission object (autosave/undo serialize `m` wholesale; verified blob-size parity in-browser).

- **Solved burn (`physSolveNodeBurn`)**: for an existing node-map MANEUVER, the departure state is a circular parking orbit around `fromOrbit.body` at its mean altitude; the burn POINT is chosen by **analytic phasing** (`physPhaseBurnAngle`): the Hohmann-style transfer spans π of true anomaly, so the burn point sits diametrically opposite the destination's railed position (`progBodyAngleAt`) at `t_dep + TOF_schematic` (same geometry as 574's `_trajArcRotationForTarget`). Interplanetary legs use the same rule against the destination planet's heliocentric angle — deliberately coarse; P4's shooter refines aim. The burn VECTOR is prograde with **magnitude taken verbatim from the existing ΔV engine** (`progNmComputeEdgeDv` / `dvOverride`) — ΔV *required* accounting is therefore byte-identical with physics on vs off (verified: Apollo seed 3,143 / 822 m/s unchanged).
- **Leg propagation (`physRebuildMissionTrajectories`)**, called at the `missionRecompute` tail before autosave/undo/checks: injection legs (→ transit corridor) are propagated with `physPropagateSegment` (ctx bodies Earth/Moon/Sun cislunar, Sun/Earth/planet interplanetary) to 1.5× the schematic TOF; `converged` records whether the trajectory actually entered the destination SOI (a miss is EXPECTED pre-P4 and recorded honestly). Same-body legs are pure two-body: 64 analytic `physKeplerPropagate` samples, no integrator (perf; null-return handled). The EXITING corridor leg (TLC→LLO) carries no propagation of its own — the injection leg already flew it — but receives the physics coast TOF from that propagation's SOI-entry/periapsis timing.
- **Duration precedence** is now `durationOverride > physics leg TOF > launchWindow > Hohmann` (the last two inside `progTransferTOF`). **Stale-by-one convergence dance**: durations are consumed DURING replay but legs are built AFTER it, so replay N reads the side-table from rebuild N−1 (`physMissionRecomputeBegin` rotates current→previous at recompute top; `physLegTofFor` only trusts a leg whose from/to nodes and departure MET still match). After each rebuild, any leg whose physics TOF disagrees >1% with the duration the replay actually used triggers exactly ONE extra recompute pass (`_physRecomputePass` depth guard — never loops). Measured on the Apollo seed: the TLC coast shortened from the schematic 430,059 s Hohmann to the propagated 406,480 s Moon-SOI periapsis arrival, converging in one extra pass; full recompute incl. both passes ≈ 12 ms (< 50 ms budget).
- **Reconciliation delta (Apollo seed, physics on vs off)**: ΔV *required* and injection propellant identical (3,143 m/s / 79,111 kg). The LOI leg's *delivered* ΔV and propellant shift 638→639 m/s and 9,959→9,967 kg — NOT a burn-model change but the physics TOF shortening the coast ~6.5 h, so cryo boiloff over the coast drops and slightly more propellant survives to the arrival burn. This is the intended consequence of physics TOF joining the duration chain (boiloff is a function of coast time, §5 T2).
- **MNODE** (`{type:'MNODE', at:{kind:'met', value_s}, dvPro_ms, dvRad_ms, dvNrm_ms}`, authored via `missionExecManeuverNode` — console/API only until P4's dock UI): burns propellant through the SAME rocket-equation path as MANEUVER burn steps with |Δv| = √(pro²+rad²+nrm²); advances NO orbit state.

## Critiques (known weaknesses, roughly by severity)

**Ascent model**
1. K3/K4/T3s/Tmix are fitted empirical constants of unstated provenance and envelope. They validate well against 1960s–present orbital LVs (Saturn V, F9 land within a few % of published capability), but nothing warns the user when a design leaves the fit's envelope (TWR ≪ 1.2 at liftoff, very lofted or depressed trajectories, air-launch).
2. Single static Isp per stage/engine — no altitude dependence. First-stage numbers are whatever the data author blended by hand; two vehicles with identical physics but different Isp-averaging conventions aren't comparable at the few-percent level.
3. The booster integrator blends Isp correctly per interval, but the Townsend penalty is computed from aggregate `A0`/`Isp_avg`/`Ta` — parallel-staged vehicles get a serial-equivalent loss estimate.
4. `Ta`'s fractional-stage interpolation uses an exponential prop-fraction heuristic, not the actual time-to-Vcirc within the stage.

**Destination ΔV**
5. Plane-change logic assumes initial inclination = |site latitude| and charges nothing for inclinations above latitude (real azimuth constraints and range-safety corridors can make those expensive). Retrograde/SSO targets are only "charged" via lost rotation credit.
6. The combined-plane-change-at-apo optimization triggers on an arbitrary `apogee > 10,000 km` threshold; elliptical targets never get the combined treatment (plane change added scalar, not vectorially).
7. Tolerance constants (5 km "circular", 50 km "same perigee", 0.5° plane-change deadband) are unlabeled magic numbers.
8. Escape declination penalty is a crude great-circle plane change at parking speed; no DLA/azimuth interaction.

**S1.5**
9. BECO located on stage-only mass (payload ignored) — the "< 5 %" error claim is asserted, not tested, outside Atlas-class proportions.
10. Phase-1 blend (when used) is static; booster-pack jettison is instantaneous with no thrust decay, and `s15_beco_twr` defaults to 1.2 regardless of vehicle.
10a. The blend's sustainer term uses `s15_sust_isp`, which the library stores as the VACUUM value (it primarily serves Phase 2) — so the Phase-1 blend is optimistic at low altitude, where the sustainer's real SL Isp is far worse (LR-105: ~215 s SL vs 309 s vac). With Atlas data the blend RAISED Ph.1 Isp (282 → 285.5 s) rather than lowering it. To make the blend represent liftoff conditions you'd need a separate sea-level sustainer Isp field, or the user must fold the pessimism into `s15_boost_isp`. Known and accepted for now.

**Mission / node map**
11. Two ascent models coexist: Townsend (when LV performance data exists) vs `Vcirc + fixed-loss table`. A mission can silently switch fidelity depending on how the vehicle was created. The loss table itself (Earth 1550 etc.) is a rough constant independent of TWR or target altitude.
12. LOI/TEI patched-conic underestimates (~10 %, documented); TEI = LOI symmetry is a simplification; no free-return or finite-burn losses anywhere.
13. Interplanetary transfers: circular coplanar planets, no plane change, no arrival-timing coupling between the node map ΔVs and the porkchop's Lambert solutions — the two subsystems can disagree about the same trip.
14. Docking tolerance windows (1 km, 0.1°, 1° LAN) are arbitrary, and `epoch`/phasing is entirely ignored — co-orbital ≠ co-located.
15. Lunar/Mars ascent = scaled constants; no TWR sensitivity, no plane targeting from launch site latitude on those bodies.
16. Boiloff: constant fractional rate, insulation as a linear multiplier in the exponent; no tank thermal state, no ullage/pressurization losses. Rate is constant over the whole coast regardless of duration — a 261-day cislunar loiter and a 3-day one lose mass on the exact same exponential curve, with no allowance for a tank's fill fraction changing its effective surface-to-volume ratio over time.
16f. Propellant-type provenance is asymmetric and easy to get wrong silently: launch-vehicle stages always get a valid cryo/storable type (Isp-inferred by `progVehicleDefToLiveStages`), so they DO boil off; spacecraft stage definitions default to `propType: 'MMH/NTO'`, which is not a registered key in `PROG_PROPELLANT_TYPES` — an unedited spacecraft stage therefore boils off NOTHING, not because MMH/NTO is storable (it correctly would be, if modeled) but because the lookup silently misses. The net effect (storable-by-default) happens to be physically reasonable for a real MMH/NTO service module, but it's an accident of naming, not a deliberate default — a future propellant type added to the registry under a different key would need to also update this default, and nothing enforces the two stay in sync.
16g. Boiloff during LAUNCH ascent is modeled (applied, not skipped) but negligible by construction — ascent burn times are minutes, and the exponential over minutes is indistinguishable from zero at any realistic cryo rate. Documented rather than special-cased to avoid a silent gap in the "every clock advance boils off" invariant.

**Mission time (T1)**
16a. Hohmann-model TOF ≠ real trajectories: the translunar half-ellipse estimate lands ~5 days vs. Apollo's actual ~3-day free-return trajectory — the model doesn't know about faster non-Hohmann transfers, and overrides are the intended escape hatch for any mission that needs an accurate date.
16b. All burns (BURN and MANEUVER) are treated as impulsive/instantaneous in the clock — only the COAST/transfer between them accumulates time. A long low-thrust burn would in reality itself take meaningful time; not modeled.
16c. Interplanetary TOF ignores launch-window phasing (planets aren't actually where a Hohmann departure needs them) unless the mission has a specific porkchop-selected Lambert window (`PROG_ACTIVE_PROGRAM.launchWindow`) — absent that, the number is a generic Hohmann estimate, not a real date.
16d. `durationOverride`/`dvOverride` intentionally bypass the physics by design — they exist so the user can substitute a known real value (e.g. actual Apollo TOF/ΔV) for the model's estimate. The UI badges overridden events "(custom)" so this is never silently confused with the computed value, but nothing prevents an override that's physically inconsistent with the vehicle's actual propellant/ΔV budget beyond the normal margin checks.
16e. Transit-corridor convention: a coast is charged once, on the leg EXITING the corridor node (TLC→LLO carries the ~5 d translunar TOF; LEO→TLC is the impulsive injection, 0 s). Found the hard way: the first implementation charged both legs and doubled every corridor transit.

**Boiloff on clock advancement (T2)**
16h. Boiloff is applied to EVERY live vehicle whenever ANY vehicle's clock-advancing event fires — a docked depot idling in LEO boils off in step with the vehicle actually coasting to the Moon, which is physically correct (time passes for everyone), but it means a mission with many idle vehicles pays the boiloff cost once per clock-advancing event rather than once per vehicle-day, which is the same total mass loss but a different (equivalent) computational path worth noting for anyone auditing `applyMissionBoiloff` in `missionRecompute` (570).
16i. The readiness check's cumulative-boiloff percentage (572, `boiloff-losses`) divides by "initial propellant capacity," which is captured at LAUNCH/DEPLOY time (`fv._initialPropCap`). A vehicle born mid-mission from a SEPARATE or DOCK (no LAUNCH/DEPLOY of its own) has no cached initial value; the check falls back to that vehicle's CURRENT capacity at the moment boiloff is first detected, which understates the percentage for any vehicle whose stages were combined after already losing propellant to burns — a known, documented approximation, not a hard guarantee.

**Body kinematics (C1a)**
16j. No ephemeris: `progBodyAngleAt`/`progBodyWorldPos` are internally consistent (self-referential angles that advance correctly relative to each other and to the porkchop's calibration), not astronomically true — the Moon is NOT actually at 0° on any real date the app might imply, and nothing ties `t=0` to a calendar date.
16k. Planet and moon orbits are modeled as perfectly circular (no eccentricity, no elliptical speed variation) — real orbital radius/speed variation over an orbit is not represented.
16l. Everything is coplanar — no inclination between planets, and moon orbits are drawn in their parent's equatorial-schematic plane with no relative plane tilt (e.g. the real Moon's ~5° inclination to the ecliptic is absent).

**Trade studies**
17. Inclination/altitude sweeps use the minimal circular-orbit ΔV replica (clearly labeled) — fine for trends, not for elliptical or escape comparisons.
18. Tornado is one-at-a-time and symmetric: no parameter interactions, no asymmetric sensitivities (e.g. Isp loss usually hurts more than gain helps near margin limits).

**Trajectory view LOD + mission-state rendering (C2)**
21. Vehicle-on-arc position (`_trajArcPointAt` driven by `_trajLegPathFraction`) is uniform PATH-LENGTH-ANGLE progress along the drawn half-ellipse, not true orbital motion — real vehicles move faster near periapsis (non-uniform true-anomaly rate under Kepler's second law), so the dot's on-screen speed is constant while a real vehicle's isn't. Schematic "roughly here" indicator only.
22. The Moon-frame patched-conic seam fallback (`_trajLocalRadius`'s `max(2×bodyR, 0.5×mo.r)` departure radius for a transit arriving at its own destination frame) is an arbitrary rendering placeholder, not a Hill-sphere/SOI calculation — it exists purely so the arc has SOME finite departure point to draw from in the destination's own frame; the radius value carries no physical meaning (it's tuned to clear the transferArc LOD window's px floor across camera anchors, not to model the real hyperbolic approach geometry).
23. Orbit-ring "history" dimming only tracks vehicle-LEVEL EXPEND events (`expendMetByOwner`, keyed by originKey) — a stage-level EXPEND (partial jettison) doesn't retire the ring's owner, so a ring whose vehicle survives via a remaining stage never dims even if the specific stage that occupied that orbit is long gone.
24. The zone-of-influence fade-in threshold (~30px neighborhood extent) and the LOD ramp's "20% of `lo`" cap are both hand-tuned constants with no derivation beyond "looked right in testing" — same category as the pre-existing magic-number critiques elsewhere in this document (see critique 7).
25. **Planet-phase calibration is per-mission fiction, purely for renderability.** Two different missions transferring to Mars at the same MET can render Mars in visibly different positions, because each mission's calibration offset is solved independently from that mission's own first leg's departure/arrival timing — there is no shared "true" Mars position across missions (or against the porkchop plotter, which uses uncalibrated table `theta0`s). This is a rendering-layer patch on top of the existing non-ephemeris critique (16j) — it does not add or remove any physical accuracy, it just makes ONE mission's own interplanetary arc visually close instead of visibly missing its target. A second leg to an already-calibrated planet within the same mission can't be satisfied at all (only the first leg gets to calibrate) and is intentionally rendered as a schematic ghost (dashed endpoints + dotted line) rather than a misleading connecting arc.
26. **Zone-of-influence gate blocks mission content at moonless-planet camera anchors** (found while implementing planet-phase calibration, not introduced by it — pre-existing): `_trajWorldSVG`'s per-planet `zoiAlpha` computation is `Math.max(neighborhoodExtentPx, _trajBodyNeighborhoodPx(body, zoom))` against the `zoneOfInfluence` window's 30px floor, but `neighborhoodExtentPx` is a fixed 6px clamp by construction of `_trajBodyPxR` (not derived from actual mission-content extent) and `_trajBodyNeighborhoodPx` only considers a body's MOONS. A moonless planet (Mars, Venus, Mercury, etc.) therefore NEVER opens its own zone-of-influence at any zoom, so its transfer arcs and orbit rings never render — verified in-browser (a Mars-orbit mission leg's arc stayed invisible with the camera anchored directly on Mars, at every tested `cam.wKm`; content only became visible after monkeypatching `_trajBodyNeighborhoodPx` in a debug session, confirming the extraction/geometry itself is correct and only the LOD gate is at fault). This is a real user-facing gap (the planet focus-bar button flies exactly to this camera state) — flagged as a follow-up task, not fixed here (out of this change's scope: `574-trajectory-view.js`'s general LOD architecture, not the calibration feature itself). — FIXED (2026-07-09): the ZOI gate and the fly-to fit now share one neighborhood definition (_trajBodyNeighborhoodKm: moon rings, mission-content extent, 4R floor), so any camera that frames content opens the gate that draws it.

27. **Physics core (P0, 385) rails are circular and coplanar** — `physBodyStateAt` velocities are exact only for the circular-rail fiction the kinematics table defines (real planetary e ≈ 0.01–0.2 ignored, consistent with critique 16j). `physKeplerPropagate` returns `null` on Newton non-convergence (near-parabolic + extreme dt corners) — every future consumer (P1+) MUST handle the null rather than assume a state; nothing consumes it yet.
28. **Integrator (P1, 386) accuracy is schematic-grade, not ephemeris-grade**: 2nd-order leapfrog at 360 steps/orbit accumulates ~0.3 km/orbit of phase error, and Jacobi fidelity is ~1e-3 on high-e lunar encounters — fine for illustrating free returns and flybys, NOT for real trajectory design. Close-approach accuracy also depends on the step ladder catching the encounter: a vessel screaming through the Moon's SOI at a coarse cruise step takes its first fine step only AFTER the SOI event is detected (transition location error up to one coarse step). The rails' 0.3% ω²d³ vs μ inconsistency (real Moon period + real μ don't satisfy the circular-rail identity) is absorbed as a permanent small perturbation.
29. **SOI transitions are detected, not bisected, in P1**: the handoff happens at the first step-end INSIDE the new sphere rather than at the exact boundary crossing (physFindEventTime exists but isn't wired into the transition path yet) — a deliberate simplification; revisit if P4 shooter convergence turns out to be sensitive to the patch point.
30. **P2 analytic phasing is aim, not targeting**: `physSolveNodeBurn` places the burn point assuming a pure Hohmann half-ellipse in a two-body field, then propagates in the FULL perturbed field — lunar gravity bends the real trajectory, so the propagated leg generally arrives near, not at, the Moon (recorded as SOI-entry `converged` metadata; a clean miss is legal and expected until P4's differential corrector). Interplanetary phasing is cruder still: the LEO burn point is placed at a schematic heliocentric angle with no ejection-asymptote geometry (that arrives in P3's `physEscapeGeometry`).
31. **MNODE honesty gap (P2)**: an MNODE burns real propellant through the rocket equation but advances NO orbit state — the node-map orbit and the physics-side trajectory diverge silently after any MNODE. The band/orbit views keep showing the pre-burn orbit. P3 (render from side-table) and P4 (authoring UI + shooter) close this; until then MNODE is a console-only accounting event.
32. **P2 physics TOF is stale-by-one**: the duration a replay uses comes from the PREVIOUS rebuild's legs, reconciled by at most one extra recompute pass per edit. If an edit changes an upstream duration, downstream legs fall back to schematic TOF for that single pass (their MET signature no longer matches) — momentarily inconsistent durations inside one recompute cycle are possible by design, never persisted.
33. **P2 delivered-ΔV coupling through boiloff**: because physics TOF changes coast durations and boiloff is time-dependent, enabling physics shifts *delivered* ΔV/propellant on cryo missions slightly (Apollo seed: +1 m/s / +8 kg on LOI) even though *required* ΔV is byte-identical. Anyone diffing mission totals across the P2 boundary must compare required, not delivered, figures.
