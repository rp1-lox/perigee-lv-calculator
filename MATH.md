# MATH.md — Rocket Playground Methodology

Every physics calculation in the program, where it lives, what it assumes, and where it's weak. **This file is load-bearing: if you change any math, update this file in the same commit** (CLAUDE.md enforces this). Critiques are collected at the bottom — add to them honestly when you spot a weakness; they are the to-do list for model quality.

Conventions: masses kg · thrust kN (converted to N internally) · Isp seconds · ΔV m/s unless noted · altitudes km above surface · `G0 = 9.80665 m/s²` · Earth `MU` (km³/s²) and `RE` (km) in `010-constants.js` · other bodies in `PROG_BODIES`. Every stage/engine carries ONE representative Isp — there is no altitude-dependent Isp anywhere in the program; users choose sea-level, vacuum, or trajectory-averaged values by convention (typically SL-ish for first stages, vacuum for uppers).

---

## 1. Rocket equation (the foundation)

`rocketEq(isp, m0, mf)` (140-physics.js) — Tsiolkovsky:

```
ΔV = g0 · Isp · ln(m0 / mf)
```

Degenerate inputs (mf ≤ 0, m0 ≤ mf) return 0. The program-side twins `progRocketEqDv(m_wet, m_prop_consumed, isp)` and its inverse `progRocketEqPropNeeded(m_wet, dv, isp) = m_wet·(1 − e^(−ΔV/(g0·Isp)))` live in 380 and drive mission burns.

Usable propellant everywhere excludes residuals: `prop_usable = prop · (1 − res/100)`.

## 2. Launch performance — the Townsend-Schilling model

`lvPerformance(stages, booster, pay, fairingMass, fairingJ, parkingAlt, onOrbitDV, siteLat, azMin, azMax)` (140-physics.js) is the single source of truth for ascent performance — the LV calculator, the mission LAUNCH event, the orbits-page vehicle selector, and every trade-study sweep all call it. It is an **empirical ΔV-budget model**, not a trajectory integrator: no altitude, drag, or pitch profile is simulated. Structure:

**2.1 Ideal ΔV per stage.** Serial stages burn bottom-up. For stage s with payload-above mass `spM[s]` (all stages above + payload + fairing while attached):

```
m0 = dry + prop_usable + spM[s],  mf = dry + spM[s]
ΔV_s = rocketEq(isp, m0, mf);   burn time bt_s = prop_usable / ṁ,  ṁ = F/(g0·Isp)
```

**2.2 Parallel boosters — event-driven integrator.** When booster groups exist, stage 0's ΔV/burn-time are replaced by a piecewise integration: between "events" (a group igniting at T-0 / after a predecessor / at a fixed time; a group or the core running dry) the active engine set is constant, so each interval is one rocket-equation step at the **blended effective Isp**:

```
Isp_eff = ΣF / (Σṁ · g0)        (true thrust-weighted harmonic mean, per interval)
```

Per-group `parallelMode`: `independent` (each burns its own tanks), `crossfeed` (boosters feed the core — the core reaches staging with full tanks; core mass-flow is drawn from the booster groups evenly), `throttle` (the core throttles to `coreThrottle` while that group burns — also reduces liftoff thrust). Spent groups drop their dry mass immediately. A guard caps the loop at 500 events. This block reduces exactly to the plain serial computation for a single ground-lit group (regression-tested).

**2.3 Gravity + drag losses (the empirical core).** With `Hp = parkingAlt` (km):

```
K3 = 429.9 + 1.602·Hp + 1.224e-3·Hp²         (m/s)
K4 = 2.328 − 9.687e-4·Hp                      (m/s per second)
T3s = 3·(1 − e^(−0.333·Vcirc/(g0·Isp_avg)))·g0·Isp_avg / A0
Tmix = 0.405·Ta + 0.595·T3s
ΔV_penalty = K3 + K4·Tmix
```

where `A0` = liftoff thrust / liftoff mass, `Isp_avg` = burn-time-weighted average Isp, and `Ta` = burn time **only up to reaching Vcirc** (fractional within the crossing stage via an exponential prop-fraction interpolation) — deliberately so low-thrust upper stages aren't charged gravity/drag losses for burns that happen after insertion. The K3/K4/T3s forms and the 0.405/0.595 mix are fitted constants from the Townsend/Schilling launch-performance estimation method; treat them as a package — do not tune individual constants without re-validating against known vehicles.

**2.4 Earth rotation credit.** `rotVel(lat, azMin, azMax)`: `V_rot = ωE·RE·cos(lat)·cos(az−90°)`, maximized over {azMin, azMax, 90°} and clamped to [0, ωE·RE·cos(lat)]. A site whose azimuth window excludes due east gets partial credit.

**2.5 The budget.**

```
DVasc = Vcirc + ΔV_penalty − V_rot
DVtot = DVasc + onOrbitDV
margin = ΣΔV_s − DVtot
```

**2.6 Max payload.** `lvMaxPayload(...)`: 40-iteration bisection on payload ∈ [0, 2,000,000 kg] for margin = 0 (margin is monotonically decreasing in payload, so bisection is valid). Returns 0 if even zero payload has negative margin.

## 3. Destination ΔV (`onOrbitDV`)

Two implementations that MUST agree: the original inside frozen `calculate()` (160) and the pure transcription `destOnOrbitDV(dest, siteLat)` (145) — pinned together by regression goldens captured from the real calculate() (tests/math.test.js). All burns are impulsive, all transfers two-body Earth.

**Orbit mode** (target apogee/perigee/inc from a circular parking orbit at `parkingAlt`), with `vPeri/vApo` from vis-viva:
- Target ≈ parking (both within 5 km): 0.
- Circular target (|apo−peri| < 5 km): Hohmann `dv1 = |v_peri(transfer) − Vc_park|`, then either
  - **combined plane change at apoapsis** if a plane change is needed AND apogee > 10,000 km: `√(va² + vc² − 2·va·vc·cosθ)` replacing the circularization burn (the classic GEO trick), or
  - separate circularization + plane change at parking-orbit speed: `2·Vc·sin(θ/2)`.
- Elliptical target: `dv1` raises apogee, `dv2 = |vApo(target) − vApo(transfer)|` adjusts perigee at apoapsis (skipped when |perigee − parkingAlt| < 50 km), plane change added separately (never combined).
- Plane change is only charged when `inc < |siteLat| − 0.5°` — the model assumes launch inclination = site latitude (minimum-inclination due-east launch) and that HIGHER-than-latitude inclinations are reachable by launch azimuth at no ΔV cost (the azimuth window only affects V_rot).

**Escape mode** (C3, declination): from vis-viva at the parking perigee,

```
V_inj = √(Vesc² + C3),  Vesc² = 2μ/r     →  onOrbitDV = V_inj − Vcirc(parking)
```

plus a declination plane-change penalty `2·Vc·sin(Δ/2·...)` when |siteLat| exceeds |declination| by > 0.5° (Δ = the excess). C3 below −Vesc² is rejected as an error.

## 4. Stage-and-a-half (S1.5)

`_s15BecoSplit(s)` (150). An S1.5 stage (Atlas-style: jettisonable booster engines + continuing sustainer) is split into two virtual serial phases before ANY physics:

- **BECO point** from a jettison-TWR criterion using **stage-only mass** (payload above is deliberately ignored; the comment claims < 5 % ΔV error for Atlas-class): `m_after = F_sust/(twr·g0)`; propellant before BECO is `prop_ph1 = (dry+prop) − (m_after + jet_mass)`.
- **Phase 1** (all engines): thrust = authored stage thrust; Isp = the authored stage Isp, OR — when the optional `s15_boost_isp` field is present — the **mass-flow blend** `Isp_ph1 = F_tot / ((F_tot−F_sust)/Isp_boost + F_sust/Isp_sust)`. Note the sustainer term reuses `s15_sust_isp` (stored as vacuum — see critique 10a).
- **Phase 2** (sustainer alone): thrust = `s15_sust_thrust`, Isp = `s15_sust_isp`, dry mass reduced by the jettisoned pack.

⚠️ The pure physics (`lvPerformance`/`lvMaxPayload`) knows nothing about s15 fields — every consumer must expand first. Splitters: `calculateWithS15` (worksheet), `_fleetExpandStages` (560), `_tsExpandStages` (165, also used by 167). This invariant has been violated twice; the gate has an Atlas golden guarding it.

## 5. Mission engine (program mode)

**Live stages** (370): a stage instance = dry mass + tanks (`fill`/`capacity` per propellant type). Burns drain tanks in order (`progBurnPropellant`); boiloff (`progBoiloff(fill, rate, days, insulation) = fill·e^(−rate·insulation·days)`, `progApplyStageBoiloff` applies it to every tank of a stage) is **ACTIVE (T2)**: `missionRecompute` calls it on EVERY live (non-EXPENDED/RECOVERED) vehicle's stages whenever the mission clock advances — COAST, the coast leg of a BURN (HOHMANN/TLI) or MANEUVER, and (negligibly) LAUNCH ascent time. Propellant type provenance matters here: LV stages get an Isp-inferred type from `progVehicleDefToLiveStages` (400) — always one of `LOX_LH2`/`LOX_CH4`/`LOX_RP1`, all of which have nonzero boiloff rates, so **LV stages DO boil off**. Spacecraft stages default to `propType: 'MMH/NTO'` (440) — NOT a key in `PROG_PROPELLANT_TYPES` — so an unedited spacecraft stage's tanks see `pt` resolve to `undefined` in `progApplyBoiloff` and **silently lose nothing**; only spacecraft stages whose propType is explicitly set to a `PROG_PROPELLANT_TYPES` key (e.g. `LOX_LH2`) boil off. This is a caveat, not a bug: unknown propellant = storable-by-default per critique 16f below.

**Boiloff ordering (T2)**: applied to ALL live vehicles at the point the clock advances, not just the acting one — so an idle depot boils off while another vehicle coasts/burns elsewhere. Per event type: LAUNCH — boiloff applied AFTER the ascent burn (order is immaterial; ascent is minutes, boiloff over that span is negligible — modeled but negligible, not skipped). BURN (HOHMANN/TLI) — boiloff applied AFTER the burn, for the coast LEG THAT BURN INITIATES (departure now, arrival later; matches the transit-corridor convention, critique 16e). MANEUVER — boiloff applied BEFORE the maneuver's own propellant burn, for the coast leg that PRECEDES it (the maneuver is the arrival burn ending that coast, e.g. LOI ending a TLC→LLO leg) — so a maneuver's burn draws from POST-boiloff tanks, meaning a coast that drains enough cryo propellant correctly starves the arrival burn and trips the existing burn-overdraw check (572 #2) with no separate check needed. COAST — boiloff applied for the coast's own authored `days`.

**Ascent staging** (`_missionApplyLaunch`, 570): the LAUNCH event runs `lvPerformance` on the snapshot vehicle (S1.5 expanded, boosters included in stage 0) to get `DVasc` (required) and per-stage ΔVs. It then walks stages bottom-up: stages whose full ΔV is consumed before meeting the requirement are burned dry and EXPENDED; the stage that crosses the requirement is the **insertion stage** — its propellant use comes from inverting the rocket equation on the full remaining stack (`progRocketEqPropNeeded` with mass-above included), leaving real residual propellant for later mission ΔV. Upper stages that never ignite ride to orbit untouched (there is deliberately NO forced stage-at-burnout). Spacecraft payload stages are never burned during ascent. When no performance data exists, the required ΔV falls back to `_missionDvToOrbit(body, alt) = Vcirc + fixed loss` with a per-body loss table (Earth 1550, Mars 1100, Venus 1700, Moon 20, Mercury 200, Titan 1400 m/s).

**Maneuvers** use the node-map physics (below) for required ΔV, then `progRocketEqDv/PropNeeded` against the active vehicle's stage stack. **Docking** requires `progOrbitalStateMatch`: same body, apogee/perigee within 1 km, inclination within 0.1°, LAN within 1°.

**Mission time (T1 — `missionRecompute`, 570)**: time is DERIVED from the replay, never authored as position. A mission clock (seconds) walks `m._expanded` in order; T-0 is the FIRST LAUNCH event (anything authored before it sits at T+0). Duration rules per event type:

| Event | Auto duration |
|---|---|
| LAUNCH | Ascent burn time — `lvPerformance`'s `tBT` (sum of per-stage burn times), cached onto `stagingResult.burnTime` |
| BURN (HOHMANN) | `progHohmannTOF(body, periBefore, burnParam)` — the Hohmann coast this burn initiates |
| BURN (TLI) | `progHohmannTOF('Earth', periBefore, PROG_MOON_ORBIT_R − R_Earth)` — the translunar coast |
| BURN (LOI) | 0 — arrival burn at the end of an already-counted TLI coast |
| BURN (CIRC / PLANE_CHANGE / CUSTOM) | 0 — treated as impulsive with no separate coast leg |
| MANEUVER | `progTransferTOF(fromNode, toNode)` — the coast, not the (impulsive) burn itself |
| COAST | `days × 86400` (authored — the ONLY event type where the user authors time directly; `durationOverride` is not applicable/needed here) |
| everything else (DEPLOY, SEPARATE, DOCK, EXPEND, RENDEZVOUS, transfers, REENTER, RECOVER) | 0 |

`progHohmannTOF(body, alt1_km, alt2_km)` = half-ellipse period `π·√(a³/μ)`, `a=(r1+r2)/2`. `progTransferTOF(fromNode, toNode)` classifies the node pair (mirrors `_nmDvPhysics`'s node shape): same-body circular/elliptic/surface → Hohmann half-ellipse between average altitudes; Earth → lunar transit/LLO/lunar-surface → translunar half-ellipse to `PROG_MOON_ORBIT_R`; Earth → interplanetary transit (Mars/Venus/…) → heliocentric Hohmann TOF via `PROG_HELIO_R`/`PROG_MU_SUN`, UNLESS the program has a selected Lambert launch window (`PROG_ACTIVE_PROGRAM.launchWindow.tof_days`), which is authoritative when present; anything else (surface↔surface, unmodeled pairs) → 0.

`PROG_HELIO_R` (360) now covers all eight planets (Mercury/Venus/Earth/Mars/Jupiter/Saturn/Uranus/Neptune — mean heliocentric radii, km), so `progTransferTOF`'s interplanetary branch transparently produces Hohmann TOFs for the outer planets too (previously only Mars/Venus were tabulated); critique 16c (no launch-window phasing) applies equally to these new entries — an Earth→Jupiter/Saturn/etc. TOF is a generic co-planar Hohmann estimate, not tied to an actual date. `PROG_MOON_ORBITS` (360) generalizes `PROG_MOON_ORBIT_R` into a small parent/radius map (`Moon` around Earth, `Titan` around Saturn at 1,221,900 km) for the Trajectory view's local-scene rings; it is not yet consumed by `progTransferTOF` (which still special-cases Earth↔Moon directly) — a future TOF generalization to arbitrary moon systems should read from this map instead of hand-adding cases.

**Overrides**: each log entry may carry `durationOverride` (seconds) and, for MANEUVER, `dvOverride` (m/s) — both authored fields that ride undo/autosave for free since they live on `m.log`. `durationOverride` replaces the auto duration in the clock accumulation. `dvOverride` replaces the node-map-computed ΔV requirement **before** propellant computation in `_missionApplyManeuver`, so the rocket equation (and everything downstream — flight-readiness checks, state-panel numbers) consumes the custom value consistently; there is no separate override-aware code path to keep in sync. Both are cached alongside the auto value (`e.durationAuto`/`e.durationUsed`, `e.dvAuto`/`e.dvRequired`) so the UI can badge overridden events "(custom)" and offer "reset to auto". `_metFmt(sec)` renders the running clock as `T+MM:SS` / `T+HH:MM` / `T+Nd HH:MM`; display only, never fed back into layout or physics.

## 6. Node-map ΔV physics (360 + 430)

`progNmComputeEdgeDv(from, to)` → `_nmDvPhysics`: same-body transfers compose Hohmann legs (`progDvHohmann`, vis-viva exact), plane changes (`progDvPlaneChange = 2v·sin(θ/2)`; `progDvPlaneChangeFull` gets the true angle between planes from the spherical law of cosines `cosθ = cos i1·cos i2 + sin i1·sin i2·cos ΔLAN`; `progDvCombined` vector-adds a plane change with a coplanar burn), and apoapsis circularization (GTO→GEO). Cross-body transfers are **patched conics with impulsive burns**:

- **TLI**: Hohmann from LEO to the Moon's orbital radius.
- **LOI/TEI**: v∞ at the Moon = |v_moon − v_apo(TLI)|, then hyperbolic-to-circular at LLO: `ΔV = √(v∞² + 2μM/r) − √(μM/r)` (the Oberth form). TEI is assumed symmetric to LOI. The code itself documents the known underestimate (~822 m/s vs ~900 real Apollo LOI with free-return constraints).
- **TMI/TVI + MOI/VOI**: heliocentric circular-coplanar Hohmann between planet orbits gives v∞ at departure/arrival; departure and capture burns use the same Oberth form at LEO/target-orbit radius. No plane change, no synodic timing (timing lives in the porkchop, separately).
- **Surface↔orbit**: Earth ascent uses the launch model; lunar/Mars ascent are scaled baselines (`1870 m/s` at LLO-100, `3810 m/s` at MCO-400, scaled by the ratio of target-orbit circular speeds). Descent numbers mirror ascent.

## 7. Porkchop plotter (410)

A real **Lambert solver** (universal variables with Stumpff functions C(ψ), S(ψ), bisection on ψ) over a departure-date × time-of-flight grid. **R1 (2026-07-09): planet positions come from the REAL ephemeris (§7a), projected to the ecliptic plane (z dropped) because `progLambert2D` is 2D** — a small error for the destinations plotted (Mars i = 1.85°, Venus 3.39°; see critique 42). `dep_day` now means **days past the program epoch (`PROG_ACTIVE_PROGRAM.epochJD`)** — departure days are real dates (default epoch 2026-07-09: the Earth→Mars optimum lands at dep_day ≈ 118 ≈ 2026-11-04, TOF ≈ 327 d, C3 ≈ 8.9 km²/s² — the actual late-2026 window; the old calibrated fiction pinned the optimum near dep_day 0 by construction). Output: C3 heatmap; the selected cell sets the program's launch window / coast duration. Independent of the node-map ΔV numbers. The grid cache is keyed by destination + epochJD.

**Now user-facing** (previously dormant machinery with no UI entry point). Mars/Venus only (`PROG_PORK_DESTINATIONS`); other transit destinations show a greyed "⚟ Launch window…" button with a tooltip instead. Entry points: the Add-Event MANEUVER form and the event edit modal, both on interplanetary legs (`toNode.orbit.type==='transit' && orbit.body==='Sun'`); a chip on maneuver cards shows the active window or "Hohmann default" and reopens the modal. The modal (`modal-mission-porkchop`, 570/410) renders the C3 heatmap onto a `<canvas>` (`progPorkRenderCanvas`, one pixel per grid cell, `image-rendering:pixelated`) with a live hover readout and click-to-stage selection; Apply commits the pending selection and calls `missionRecompute`. The heatmap's blue→red C3 ramp is a fixed perceptual gradient used as **data**, exempt from the chrome theming rules (`progPorkC3Color`) — canvas chrome/labels (axis captions, buttons) use `var(--…)` as usual.

`launchWindow` shape: `{ destination, dep_day, tof_days, c3 }` (`PROG_PORK_DESTINATIONS = ['Mars','Venus']`), stored on `PROG_ACTIVE_PROGRAM.launchWindow` and destination-keyed so a Mars window never affects a Venus leg — both `progTransferTOF` (360) and any leg-timing consumer check `lw.destination === dest` before using it. It rides `buildProgramObject()`/autosave for free since `PROG_ACTIVE_PROGRAM` is bundled wholesale (450/455) — no separate persistence path needed.

**Precedence** (highest wins): explicit per-event `durationOverride` (authored on the log entry) > selected `launchWindow` for that destination > generic Hohmann TOF estimate. Implemented once, in `progTransferTOF` (feeds `durationAuto`) and the mission replay's `durationUsed = overrideSec != null ? overrideSec : durationAuto` (570) — the window is just one of the two inputs to `durationAuto`, so no separate override-vs-window branch was needed.

## 7a. Body kinematics — REAL EPHEMERIS RAILS (R1, 2026-07-09)

**This section was rewritten for R1.** The old C1a model (circular, coplanar, uniform angular motion via `PROG_BODY_KINEMATICS`, with a per-mission "planet-phase calibration" render fiction via `progCalibratedTheta0`/`_trajGetPlanetCalibration`) is RETIRED. Bodies now ride their real orbits; real phases connect real arcs, so the calibration had nothing left to fix.

**Model** (360): full Keplerian mean elements + secular rates, evaluated at real absolute time.

- **Planets** — `PROG_BODY_ELEMENTS`: the JPL approximate mean elements (Standish, valid 1800–2050): a (AU), e, I, L, ϖ, Ω at J2000 + rates per Julian century. Frame: ecliptic-J2000, +x = vernal equinox. AU = 1.495978707e8 km.
- **Moon** — `PROG_MOON_ELEMENTS.Moon`: simplified mean elements about Earth (a = 384,400 km, e = 0.0549, i = 5.145° to the ecliptic; L/ϖ/Ω at J2000 with per-DAY rates incl. the 18.6-year node regression −0.052954°/day). **Mean-element-only** — no evection, variation, or other solar-perturbation terms (critique 41).
- **Titan** — schematic: circular at 1,221,870 km **in Saturn's orbital plane** (I/Ω copied from Saturn's J2000 elements). The real Titan orbits near Saturn's *equatorial* plane, tilted ~26.7° from its orbital plane — deliberately wrong-but-simple (critique 43).

**Epoch**: MET 0 = `PROG_ACTIVE_PROGRAM.epochJD` (Julian date; default `PROG_DEFAULT_EPOCH_JD = 2461230.5` = 2026-07-09 00:00 UTC — "missions start today"). Absolute time for element evaluation = `(epochJD − 2451545.0)·86400 + MET_seconds`. epochJD persists with the program object (rides `buildProgramObject()`/autosave/session wholesale; `applyProgramObject` applies the default to pre-R1 files). **No epoch UI yet** (critique 45).

**Evaluation** (`progBodyLocalEphemState` → `_progElementsEval`, 360): elements at time T → ω = ϖ−Ω, M = L−ϖ (normalized); Kepler's equation M = E − e·sinE by Newton (tol 1e-8, `progKeplerSolveE`); perifocal position (a(cosE−e), b·sinE); rotation R3(−Ω)R1(−i)R3(−ω) into ecliptic-J2000. **Velocity is analytic, never finite-differenced**: perifocal Ė-form with the TABLE's mean-motion rate dM/dt = L̇−ϖ̇ (for the Moon this differs ~0.5% from √(μ/a³) — the real lunar rate is solar-perturbed; using the table rate keeps position and velocity mutually consistent), plus the secular frame-rotation terms Ω̇·(ẑ×r) + ω̇·(ĥ×r) (the Moon's node regression alone contributes ~4 m/s — needed to meet the gate's 1e-3 km/s velocity-consistency pin).

**API surface** (all pure):
- `progBodyEphemState(body, t_s)` → heliocentric 3D `{r:[x,y,z], v}` km, km/s; recursive for moons (parent + local). The ONE body-position source.
- `physBodyStateAt(body, t_s, overrides)` (385) is now a thin wrapper over it; `overrides` is accepted and IGNORED (signature compatibility).
- `progBodyWorldPos(body, t_s)` → `{x, y, z}` (renderer reads x/y — top-down ecliptic projection; z carried for R2's 3D camera).
- `progBodyWorldPosCalibrated(body, t_s, overrides)` → **compatibility alias** that ignores `overrides` and returns the real position. Every legacy call site (574/565) kept compiling; the calibration machinery behind it (`progCalibratedTheta0`, `_trajGetPlanetCalibration`, `_trajCalibrationCache`, second-leg ghost rendering, overrides threading in 565, the "planet phases calibrated" footer) was deleted.
- `progBodyAngleAt(body, t_s)` → atan2 of the real in-plane position (planets heliocentric, moons parent-relative), normalized [0, 2π) — the angle consumers (phasing in 565, moon-lead arc rotation in 574) now phase against reality.

**Render coherence (this phase)**: the top-down view still draws heliocentric/moon rings as SCHEMATIC CIRCLES at `PROG_HELIO_R`/`PROG_MOON_ORBITS.r` while glyphs sit at their real positions — an eccentric planet visibly sits off its ring (Mercury: real r 4.60e7–6.98e7 km vs ring 5.79e7; measured ~24 px off at Mercury-fit zoom). This visibly-honest mismatch is stated in the view footer; R2 replaces the rings with true sampled orbits (critique 40).

**Gate pins (R1)**: Earth |r| at epoch ∈ [1.467e8, 1.53e8] km and perihelion/aphelion in real bands; Mercury implied e ≈ 0.2056 from min/max radius; Moon |z| amplitude ∈ [30,000, 38,000] km over a month and geocentric distance spans the real 363k–405k km band; analytic-vs-numeric velocity < 1e-3 km/s (Earth, Moon, Titan); epoch shift of +365.25 d returns Earth to within 2e5 km; porkchop optimum at the real 2026 Mars window; `progBodyWorldPosCalibrated` alias ignores overrides.

**View-time rule** (unchanged from C1a): the trajectory view's `_trajViewTime(m)` (574) picks the time used to place body glyphs — selected event's post-event time (`metStart + durationUsed`), else `m._metTotal`, else 0.

## 7b. Trajectory view LOD ramps + mission-state rendering (C2)

**LOD opacity windows**: `_trajLodOpacity(sizePx, lo, hi)` (574) replaces C1b's hard visibility culls with a linear fade — 0 below `lo`, 1 through the middle of the window, a ramp back to 0 approaching `hi` (finite windows only). Ramp width is `min((hi-lo)*0.2, lo*0.2)` — capped at 20% of `lo` itself, not 20% of the full span, because every window in this app pairs a small `lo` (8-30px) with a huge `hi` (15x the viewport diagonal, i.e. "effectively never fades back out") — an uncapped 20%-of-span ramp would be thousands of px wide and make anything just past `lo` read as nearly invisible. `hi = Infinity` (or any non-finite/≤lo value) selects "fade in only, no ceiling" mode, used by the zone-of-influence window. Windows (feature: `[lo px, hi multiplier of viewport diagonal]`): heliocentric planet ring `[8, 15x]`; moon ring `[10, 15x]` (inherited from parent, see below — not applied standalone); mission orbit ring `[12, 15x]`; transfer arc `[10, 15x]`; zone-of-influence `[30, ∞]` (fade-in only). Body discs keep their pre-existing min-px clamp + true-scale rule with NO fade (a body is always at least visible).

**One fade authority per feature**: a moon's ring and a body's embedded mission content (its own moons + mission orbit rings/arcs) do NOT apply their own LOD window on top of their parent's — they inherit the parent body's zone-of-influence alpha (`parentZoiAlpha` / `zoiAlpha` in `_trajWorldSVG`) as a single multiplicative wrapper `<g opacity="...">`. A ring's own window (`missionOrbitRing`, `transferArc`) governs ONLY that feature's fade within an already-visible zone — it is never multiplied against the parent's zone alpha a second time.

**Far representation** (fixes the C1b zoom-out handoff): a planet's disc never fades (unchanged true-scale/min-clamp rule), but its NAME label is force-eligible — bypasses the normal screenSize/minSize gate — whenever `trueR * zoom < _TRAJ_MIN_BODY_PX`, i.e. whenever the disc itself has hit its min-px clamp (we're zoomed out far enough relative to THAT body that it's rendered as glyph+name rather than a legible true-scale disc). This is evaluated per-body, not tied to the ring's own visibility window, specifically because the 8 heliocentric rings span wildly different radii (Mercury's ring is tiny next to Neptune's) — at full solar zoom-out every body is equally "far" even though its ring's own LOD alpha may already be 0. Overlay symbology (labels/markers) inherits its parent feature's resolved alpha via a `opacity` field threaded through `_trajRegisterLabel`/`_trajResolveLabels` — a label still needs BOTH its feature's alpha > 0 AND its own size/collision gate to render.

**Corridor state rings are gone**: `_trajCorridorMoon` (a peri≈LEO / apo≈moon-orbital-radius snapshot detector) now SUPPRESSES ring generation entirely at the extraction layer (`addOrbitRing` returns `null` for a corridor-shaped snapshot) rather than relabeling it "TLC corridor" — transfer arcs carry all transit meaning now, so a mid-coast vehicle snapshot no longer draws a redundant giant ellipse ring alongside its arc.

**Moon-lead arc orientation**: `_trajArcRotationForTarget(ox, oy, targetX, targetY)` (pure) solves the transfer-arc rotation so its arrival endpoint lands on a specific target point rather than a fixed schematic angle. Derivation: `_trajTransferArcPath`'s arrival endpoint (local `(-rApo·scale, 0)`, since periapsis is fixed at local angle 0) lands at screen angle `180° + rotDeg` after rotation, so `rotDeg = atan2(dy,dx)·180/π − 180` (normalized to `(-180°,180°]`) makes it land on `(targetX,targetY)`. Applied at two sites: (a) the Sun-frame interplanetary case, target = `progBodyWorldPos(destBody, t_arrive)` where `t_arrive = leg.metArrive` (or current viewTime if the leg has no recorded arrival); (b) the local-moon case (e.g. Earth-frame TLC arriving at the Moon — though see the Moon-frame patched-conic note below for how this leg actually gets drawn), target = `progBodyAngleAt(destMoon, t_arrive)` projected onto the moon's ring. A dim dashed-outline **ghost marker** (`_trajGhostMarker`) is drawn at the arrival-time position, LOD-gated and labeled "`<body>` at arrival", ONLY when that position differs from the body's current-viewTime position by more than 3px on screen — otherwise the Moon hasn't visibly moved and the marker would just be clutter.

**Patched-conic seam in the destination's own frame** (`_trajLocalRadius`, C2 fix, then C2-review fix): a transit leg whose `destination` field equals the FRAME body itself (e.g. rendering the Moon frame, and the leg's `fromO` is `{type:'transit', destination:'Moon'}`) has no finite body-centered departure radius — the true departure point is a hyperbolic approach relative to the Moon, which this app doesn't model (patched-conic ΔV only, §6). Previously this made `_trajLocalRadius` return `null` for the departure end, so the leg's arc silently never rendered AT ALL in the destination's own frame (only the parent-frame stub burn-marker showed) — the actual TLC coast arc with its vehicle dot was invisible. Fix: a schematic fallback returns a finite "SOI edge" departure point, giving the arc a finite (if arbitrary) starting radius to draw from. **Follow-up fix (C2 acceptance review):** the fallback originally used `20 × the destination body's OWN radius` (~34,748 km for the Moon) — a value with no relationship to the actual departure-arrival gap. Because every LOD gate in this file is evaluated in real screen px (one-fade-authority rule, above), that made the leg's visibility a function of camera zoom alone: at Moon anchor the camera is zoomed in tight enough that even this tiny schematic radius reads as a large on-screen arc past the `transferArc` window's 10px floor; at Earth anchor (zoomed out to frame the whole Earth-Moon gap) the SAME arc's drawn extent collapsed under that floor and the leg silently vanished — even though the mirror leg in the parent (Earth) frame, which correctly uses the moon's full ORBITAL radius (`mo.r`) as its far endpoint, rendered fine at the same zoom. Fixed by scaling the SOI-fallback radius off `mo.r` instead (`max(2×bodyR, 0.5×mo.r)`; ~192,200 km for the Moon) so both ends of the cross-frame leg agree on the physical scale of the gap they schematically bridge, and the arc's drawn extent clears the `transferArc` LOD window's px floor with headroom at typical Earth-fit zoom (verified in-browser: ~19px vs. the 10px floor, up from ~4px pre-fix). Not a physical Hill-sphere/SOI calculation — the real value is picked purely to keep the arc's on-screen size consistent and above the LOD floor across camera anchors, not to model the true hyperbolic approach geometry (the Moon's actual Hill sphere is far smaller, ~60,000 km ≈ 0.156×mo.r).

**Mission-state trimming**: each transfer leg is classified relative to the current `viewTime` (`vt`) using its `met`/`metArrive` (both required — a zero-duration/impulsive leg, e.g. an injection burn with `met === metArrive`, always renders "planned" since it has no coast to trim): **history** (`metArrive <= vt`, dimmed to `_TRAJ_HISTORY_ALPHA = 0.35`, solid stroke) — the leg has fully completed; **current** (`met <= vt < metArrive`, full strength, solid stroke, PLUS a schematic vehicle dot) — the leg spans the current viewTime; **planned** (`met > vt`, today's dashed rendering, unchanged) — not yet departed. Orbit rings get the same history treatment when ALL their owning vehicles have a recorded vehicle-level `EXPEND` at or before `vt` (`expendMetByOwner`, keyed by `_originKey` — stage-level EXPENDs don't retire a whole vehicle so are intentionally not tracked here; a multi-owner co-located ring with even one surviving owner stays current).

**Vehicle position (schematic, NOT Kepler)**: for a "current" leg, `_trajLegPathFraction(metDepart, tof, viewT) = clamp((viewT-metDepart)/tof, 0, 1)` gives a LINEAR path-length fraction, and `_trajArcPointAt(r1,r2,scale,rotDeg,ox,oy,t)` walks the SAME half-ellipse `_trajTransferArcPath` draws (parametrized by `theta = t·π` sweeping periapsis→apoapsis) to place a dot exactly on the rendered path. **Critique**: this is uniform PATH-LENGTH-ANGLE progress, not true orbital motion — a real vehicle moves faster near periapsis (Kepler's second law / true anomaly rate is non-uniform), so the dot's on-screen speed is constant while a real vehicle's isn't. Acceptable for a schematic "where roughly is it" indicator; not a claim about real transit speed at any point along the arc.

## 7d. Physics integrator P1 — restricted n-body propagation (386)

Vessels are massless test particles; bodies ride analytic rails (`physBodyStateAt`, §7c). **Not yet consumed by mission math** (P2 wires it in). Model:

- **Frame policy**: integration happens in the vessel's dominant body's frame (its SOI), with perturbers in the standard relative-motion form — direct minus indirect tidal terms, `μ_p[(d−r)/|d−r|³ − d/|d|³]`. With one perturber this IS the restricted three-body problem in relative coordinates; it also keeps coordinates small near the body that matters.
- **SOI model**: `r_SOI = a·(μ/μ_parent)^(2/5)` (Moon ≈ 66,183 km, Earth ≈ 9.25e5 km, pinned in gate). Frame handoffs (`physPatchState`) convert position AND velocity through the shared rails; transitions are detected per-step and recorded as events.
- **Integrator**: leapfrog (kick-drift-kick), 2nd-order symplectic — energy error oscillates instead of drifting (measured ~1e-14 relative over 100 LEO orbits). Step size = local circular-orbit timescale / 360, quantized DOWN onto a fixed power-of-4 ladder (1…65,536 s) — quantization is what makes runs **bit-for-bit deterministic** (replay/undo/golden safety).
- **Events**: apsides via r·v sign change; SOI crossings; `physFindEventTime` bisection available for precise event location.
- **Single entry point**: ALL propagation goes through `physPropagateSegment` (hard invariant — no ad-hoc integrators). Sample polylines decimated to ≤ maxSamples with endpoints/frame-changes preserved.
- **Measured fidelity (2026-07-09 tuning run)**: two-body phase error ~0.3 km/orbit at LEO (vs analytic Kepler); Jacobi constant on a violent e=0.95 lunar-grazing orbit drifts ≤ 7.7e-4 relative over 15 days. **Free-return golden re-derived for R1's real rails (same day)**: old circular-rail seed (apogee 455,000 km, burn angle 4.5379 rad → 62 km return perigee) → new seed against the real eccentric/5.145°-inclined Moon: **apogee 445,000 km, burn angle 4.98 rad → 201 km return perigee** (scan: apogee × burn-angle grid, scratchpad `r1_scan.js`); pinned band [0, 2000] km unchanged.

## 7e. Physics mission bridge P2 — solved node burns (565 + 570 hooks)

First phase where the physics stack is CONSUMED by the mission model. `PHYS_ENABLED` (565, const, true) gates everything; results live in the module side-table `_physTrajByMission[missionId] = {legs}` — never on the mission object (autosave/undo serialize `m` wholesale; verified blob-size parity in-browser).

- **Solved burn (`physSolveNodeBurn`)**: for an existing node-map MANEUVER, the departure state is a circular parking orbit around `fromOrbit.body` at its mean altitude; the burn POINT is chosen by **analytic phasing** (`physPhaseBurnAngle`): the Hohmann-style transfer spans π of true anomaly, so the burn point sits diametrically opposite the destination's railed position (`progBodyAngleAt`) at `t_dep + TOF_schematic` (same geometry as 574's `_trajArcRotationForTarget`). Interplanetary legs use the same rule against the destination planet's heliocentric angle — deliberately coarse; P4's shooter refines aim. The burn VECTOR is prograde with **magnitude taken verbatim from the existing ΔV engine** (`progNmComputeEdgeDv` / `dvOverride`) — ΔV *required* accounting is therefore byte-identical with physics on vs off (verified: Apollo seed 3,143 / 822 m/s unchanged).
- **Leg propagation (`physRebuildMissionTrajectories`)**, called at the `missionRecompute` tail before autosave/undo/checks: injection legs (→ transit corridor) are propagated with `physPropagateSegment` (ctx bodies Earth/Moon/Sun cislunar, Sun/Earth/planet interplanetary) to 1.5× the schematic TOF; `converged` records whether the trajectory actually entered the destination SOI (a miss is EXPECTED pre-P4 and recorded honestly). Same-body legs are pure two-body: 64 analytic `physKeplerPropagate` samples, no integrator (perf; null-return handled). The EXITING corridor leg (TLC→LLO) carries no propagation of its own — the injection leg already flew it — but receives the physics coast TOF from that propagation's SOI-entry/periapsis timing.
- **Duration precedence** is now `durationOverride > physics leg TOF > launchWindow > Hohmann` (the last two inside `progTransferTOF`). **Stale-by-one convergence dance**: durations are consumed DURING replay but legs are built AFTER it, so replay N reads the side-table from rebuild N−1 (`physMissionRecomputeBegin` rotates current→previous at recompute top; `physLegTofFor` only trusts a leg whose from/to nodes and departure MET still match). After each rebuild, any leg whose physics TOF disagrees >1% with the duration the replay actually used triggers exactly ONE extra recompute pass (`_physRecomputePass` depth guard — never loops). Measured on the Apollo seed: the TLC coast shortened from the schematic 430,059 s Hohmann to the propagated 406,480 s Moon-SOI periapsis arrival, converging in one extra pass; full recompute incl. both passes ≈ 12 ms (< 50 ms budget).
- **Reconciliation delta (Apollo seed, physics on vs off)**: ΔV *required* and injection propellant identical (3,143 m/s / 79,111 kg). The LOI leg's *delivered* ΔV and propellant shift 638→639 m/s and 9,959→9,967 kg — NOT a burn-model change but the physics TOF shortening the coast ~6.5 h, so cryo boiloff over the coast drops and slightly more propellant survives to the arrival burn. This is the intended consequence of physics TOF joining the duration chain (boiloff is a function of coast time, §5 T2).
- **MNODE** (`{type:'MNODE', at:{kind:'met', value_s}, dvPro_ms, dvRad_ms, dvNrm_ms}`, authored via `missionExecManeuverNode` — console/API only until P4's dock UI): burns propellant through the SAME rocket-equation path as MANEUVER burn steps with |Δv| = √(pro²+rad²+nrm²); advances NO orbit state.

## 7f. Physics render integration P3 — polylines + SOI spurs (574 + 385)

First phase where the propagated trajectories are DRAWN. The trajectory view's leg loop consults the physics side-table (`physMissionLeg`, §7e) per authored MANEUVER: a hit with samples renders a **sampled polyline** instead of the schematic Hohmann half-ellipse; a miss (physics off, unconverged aim with no frame-local samples, degenerate legs) falls back to the schematic arc unchanged.

- **Continuous multi-frame drawing convention (patched-conic, KSP-style; reworked 2026-07-09 after first flight)**: leg samples are `{t, r, frame}` with `r` relative to the sample's frame body AT TIME `sample.t`. The leg's HOME pass (the frame its schematic record lives in) draws the WHOLE path as one continuous polyline: every sample maps to `anchorOf(sample.frame) + r·zoom`, where `anchorOf` resolves each frame body's CURRENT DRAWN position at viewTime (never absolute heliocentric sample positions — bodies move between sample.t and viewTime and absolute positions would smear). The original per-frame rendering made the Moon-frame passage inherit the Moon's ZOI fade, so at Earth-anchor zooms the trajectory literally vanished at the encounter and reappeared after — a continuous trajectory must never gap, so cross-frame sub-segments now bypass the destination's ZOI gate by construction (they belong to the home pass). Frame seams: the two gluings disagree by the body's drift between the handoff sample's t and viewTime, and connecting them with a chord read as a phantom straight-line burn (user-reported 2026-07-09 under the R2 tilted camera, where the gap grows) — so the polyline now BREAKS at each frame handoff and a small dashed circle marks the SOI transition (tooltip: "SOI handoff: A → B · MET"). The destination frame's arrival-leg pass emits ONLY the arrival burn marker at the clip point (no redraw, no double-draw).
- **Converged-only rule (2026-07-09; amended same day by P4)**: a physics polyline renders ONLY when the propagation reached its destination SOI (`converged`). An untargeted ballistic path is a line to nowhere on screen (first-flight Venus report) while the schematic calibrated arc DOES visually connect. **P4 update**: interplanetary and moon legs are now aimed by the differential corrector (§7g), so they normally converge and graduate to physics polylines; the schematic arc remains the fallback for legs the fixed |Δv| genuinely cannot deliver (converged:false is still legal and honest). MNODE legs (§7g) are exempt from the gate entirely — a vector burn's ballistic path IS the authored content and draws unconditionally.
- **Position coherence (R1 update — closes critique 35's calibration half for real)**: `physRebuildMissionTrajectories` phases burns against the REAL ephemeris angle and both physics and renderer resolve positions through `progBodyEphemState` — one position source, no fiction left to disagree about. (The pre-R1 text here described threading the mission's calibration overrides through physics; that machinery is deleted.)
- **Clipping**: the propagation runs to 1.5× the schematic TOF (§7e), but the drawn polyline is clipped at the EXITING leg's `metArrive` (`_trajPhysClipT`) so post-capture integrator samples don't render as a phantom continuation past the arrival burn.
- **Leg state & vehicle dot**: planned/current/history treatment is derived from the PROPAGATED span (departure MET → clip time / last sample), not the impulsive schematic record's met === metArrive. The "current" vehicle dot linearly interpolates the bracketing samples in the drawn frame at viewTime (`_trajPolylinePointAt`) — this retires the linear-path-fraction schematic (critique 21) for physics legs; sample spacing follows the integrator's step ladder, so the dot's on-screen speed is now (piecewise-linearly) Kepler-true.
- **Escape/capture spurs** (`physEscapeGeometry`, 385 — pure, gate-pinned): an interplanetary injection leg lives in the Sun frame's leg list, so the departure body's local frame previously showed nothing. P3 draws the escape hyperbola from the parking-ring periapsis out to the SOI edge (`r_SOI` per §7d): e = 1 + r_p·v∞²/μ (v∞² = C3 from the transit node spec), asymptote half-angle β = acos(1/e), conic r(ν) = p/(1+e·cosν) sampled from ν = 0 to r = r_SOI. The spur is rotated so the OUTGOING asymptote (the drawn far end) aligns with the departure body's heliocentric velocity direction — prograde for outbound (superior) destinations, retrograde for inbound — with the burn marker at the hyperbola periapsis, which sits exactly on the parking ring by construction. A mirrored **capture spur** renders at the arrival planet when no physics samples reached it (expected pre-P4): incoming asymptote anti-parallel to the schematic arrival v∞ direction (≈ −v_planet for arrivals from an inner origin), sweep mirrored. This replaces the arbitrary R×20 schematic fallback for interplanetary arrivals.
- **LOD/fade discipline**: polylines and spurs are embedded body-frame content — they inherit the body's zoiAlpha from the caller's group wrapper (one fade authority) and gate their OWN drawn extent through the existing `transferArc` px window; the extreme-end numerical culls (extent < 0.5px, > 20× viewport diagonal) apply unchanged.

## 7g. Physics targeting & authoring P4 — differential corrector, MNODE, free return (565 + 570 + 574)

The phase that makes the propagated legs actually HIT their targets, and makes MNODE a real, propagated, drawable event.

- **Generic corrector (`physShootToTarget`)**: n-DOF (n = 1 or 2) Newton iteration on x with a finite-difference Jacobian (per-component eps, default 1e-3 rad) and step-halving damping (a trial step whose miss norm grows — or goes non-finite — is halved up to 4 times; if no damped step improves, the solve terminates). Hard termination guarantees: singular/non-finite Jacobian → `converged:false`; propagation budget (`maxProps`, default 40) → `converged:false`; `maxIter` default 12. All trajectory evaluation goes through the caller-supplied `opts.propagate`, which is always `physPropagateSegment` (single-integrator invariant). Deterministic by construction (fixed eval order, no randomness, deterministic integrator).
- **ΔV accounting parity (sacred)**: for existing node-map MANEUVER legs the corrector adjusts the burn POINT (anomaly θ on the parking ring) and the burn DIRECTION (in-plane pitch off prograde) — NEVER the magnitude. |Δv| remains verbatim from `progNmComputeEdgeDv`/`dvOverride`; required-ΔV and propellant totals are byte-identical with the shooter on or off. A target unreachable at the fixed magnitude returns `converged:false` cleanly and the renderer keeps the schematic arc.
- **Leg aiming (`physShootLegAim`)**: seeds from the P2 analytic phased solve (`physSolveNodeBurn`), then shoots 1-DOF on θ with miss = closest-approach-to-destination − targetRadius (targetRadius = destination body R + the mean altitude of the first later arrival orbit in the log, else 100 km; tolerance SOI/3 — **loosened for R1** from min(SOI/3, max(1000 km, 0.25·targetRadius)) because the burn is still in the ecliptic plane while real targets are inclined: the closest approach cannot go below the target's out-of-plane offset at encounter, up to sin(5.145°)·r ≈ 36,000 km for the Moon; R3's normal-direction DOF re-tightens this). If 1-DOF stalls it escalates to 2-DOF (θ + pitch) with a second miss component pinning the closest-approach TIME to the schematic arrival (seconds × 0.5 km/s → km scale) so the 2×2 Jacobian is full-rank — chosen over the plan's `[missKm, 0]` sketch because a constant zero row is singular by construction. Closest approach prefers exact destination-frame periapsis events over (decimated) sample minima. `converged` on the stored leg still means "propagation entered the destination SOI" — the shoot result only improves aim; even an unconverged shoot's best x replaces the analytic seed.
- **Encounter step cap (`ctx.dtMax`, 386)**: heliocentric cruise otherwise reaches the 65,536 s ladder rung — ~1.5M km of relative motion per step, enough to step clean OVER a planet's SOI (found on the combined Apollo+Mars mission: the same Mars leg converged or not depending on where the coarse steps happened to land). Interplanetary legs (shooter AND rebuild propagation, which must match) cap the ladder at the 16,384 s rung — a fixed constant, so determinism is preserved; the cap merely selects a smaller rung. Cislunar legs need no cap (the ladder is already fine at lunar distances). Mercury's small SOI (~112k km) can still be step-skipped at this cap — accepted; converged:false falls back to the schematic arc honestly.
- **Shooter cache**: solutions cached in a module map keyed by `fromNode|toNode|met(0dp)|dv(1dp)` (R1 dropped the calibration-override component with the calibration itself) — re-shot only when the leg's signature changes, so a warm recompute costs ~one propagation per leg (the stale-by-one convergence pass, §7e, rides the cache for free).
- **MNODE propagation**: a vector burn takes the ACTIVE vehicle's node-map orbit at its MET (cached onto the log entry as `orbitAtBurn` by 570's replay — same derived-cache pattern as `orbitAfter`), reconstructs the mean-altitude circular ring (same reconstruction as `physSolveNodeBurn`), places the burn at anomaly θ = n·MET (circular mean-motion phase — the burn point is a deterministic function of authored MET, so no separate anomaly field is needed), applies Δv in the orbit's local frame (prograde unit + radial-out unit; **normal is ignored in the 2D world** and its input is disabled/annotated in the UI), and propagates for min(30 days, 3 post-burn periods when the new orbit stays inside 0.8·SOI). If the vehicle sits in a transit corridor or on a surface the leg records `converged:false` with a note (no parking ring to reconstruct — the corridor is a schematic, not a state). MNODE legs render UNCONDITIONALLY (no converged gate) via the same continuous multi-frame polyline path as §7f, clicking selects the event. Propellant/ΔV accounting is unchanged from §7e (|Δv| through the rocket equation).
- **Free-return template (`physFreeReturnSolve`)**: an AUTHORING solve, so here the magnitude IS free (the user is creating a new burn, not re-rendering an accounted one). 2-DOF shoot on x = [burn MET, |Δv|] — the MET dimension sweeps the burn anomaly through θ = n·MET, round-tripping exactly through the MNODE leg builder. Seeded from the R1 golden (transfer energy of a 445,000 km apogee; burn angle 4.98 rad rotated with the Moon's real in-plane ephemeris angle at departure — old circular-rail seed was 455,000 km / 4.5379 rad). Targets: lunar flyby distance at the seed trajectory's own measured value (or 0.15·SOI fallback) AND Earth return perigee in the [30, 500] km band (aimed at the seed's own perigee when already in band). With the real eccentric/inclined Moon the rotational-symmetry shortcut is only approximate (critique 38) — the corrector does real work at nonzero departure METs (measured: t=0 converges at 0 iters, t=2 d at 4 iters, both in-band). The UI prefills the Vector Burn fields with the solved values; it never auto-pushes.
- **Pinned in the gate** (14 asserts): Earth→Moon aim converges (miss < SOI/3, ≤12 iters) and the solved aim actually enters the Moon SOI; |dv| magnitude parity to 1e-12; unreachable dv/10 case returns converged:false without throwing in a bounded propagation budget; a singular-Jacobian corrector case terminates; free-return solve from 185 km LEO converges with return perigee in the P1 golden's [0, 2000] km band and a plausible 3.0–3.3 km/s magnitude; both solvers bit-deterministic across repeat calls.

## 7h. 3D physics coherence R3 — inclined vessel states, MNODE normal, shooter yaw (565 + 570, 2026-07-10)

The phase where the MISSION layer stops passing z = 0. The physics core (385/386) was 3D-native from P0; R3 makes the mission bridge construct 3D states.

- **Inclined departure states**: `physAimBurnState` (the ONE parking-ring state constructor, now shared by `physSolveNodeBurn`, the shooter, the MNODE builder and the free-return solver) builds the ring state from elements {a = r1, e = 0, i = authored inclination, **Ω = 0 convention**, ω = 0, ν = θ} via `physElementsToState` — the SAME orbit the R2 ring renderer draws, so the drawn ring and the physics orbit are one object.   - **Ring double-click → MET = current view time.** The theta→MET anomaly inversion (`theta = n·(MET − epoch)` solved backward from the clicked point's angle on the ring) was skipped in favor of the simpler, always-correct "spawn at now" — avoids a wrap-around/branch-selection edge case (multiple METs map to the same ring angle) for a first cut. ### R6.2' Phase B step 5 — solved-maneuver decomposition basis fix (565/5745, 2026-07-10)

The gizmo's handle readout for a solved maneuver (§7k's basis) and 565's display-only `dvPro_ms/dvRad_ms/dvNrm_ms` mirror on a unified `MNODE(mode:'solved')` entry both decompose the leg's real `dvVec` via `_trajGizmoDecomposeDv` against a local (v̂,r̂,ĥ) triad built by `_trajGizmoAxes(r,v)`. Through R6.2' Phase A that triad came from the MEAN-MOTION reconstruction (`_trajGizmoOrbitNodeAt`/565's mean-anomaly builder) — the right convention for a MANUAL vector burn (which literally IS authored against that reconstruction), but the WRONG anomaly for a shooter-refined moon/interplanetary leg, whose real departure point (`aim.theta/pitch/yaw` from `physShootLegAim`) sits elsewhere on the parking ring. This made a physically ~pure-prograde Apollo TLI read as pro −2085/rad +2151/nrm +950 m/s — magnitude-correct (the basis is orthonormal so `|dvVec|` round-trips exactly regardless of theta) but directionally misleading.

**Fix**: `physSolveNodeBurn`/the n-body shooter branch/the same-body analytic branch (565) now each stamp `leg.burnState = {r, v}` — the actual PRE-burn departure state the dv vector was applied to (the shooter's refined `physAimBurnState` result when converged, else the analytic seed's pre-burn state; `physAimBurnState` itself now also returns `vPre`, the circular velocity before dv is added, so callers don't need to re-subtract). Both the gizmo's `_trajGizmoManeuverNodeState` (when given a `missionId`/`authIdx`) and 565's own dv-component mirror decompose against `_trajGizmoAxes(leg.burnState.r, leg.burnState.v)` when present, falling back to the mean-motion reconstruction for legs that haven't computed a burnState (or for a genuinely manual MNODE, which correctly still wants the mean-motion basis it was authored against). ΔV ACCOUNTING is untouched by any of this — `dvRequired`/`dv_actual` still come from `progNmComputeEdgeDv`/`dvOverride` exclusively; only the pro/rad/nrm DISPLAY numbers and, per the detach fidelity note below, the DETACHED trajectory shape change.

**Detach fidelity**: dragging a handle on a solved maneuver still detaches it to a manual `MNODE(mode:'manual')` (§7k's `_trajGizmoDetachManeuverIfNeeded`), seeded with the solved pro/rad/nrm — but now the detach ALSO stamps `e.burnState = leg.burnState` (plain `{r:[...],v:[...]}` arrays, JSON-safe, rides autosave/session export fine) onto the log entry. 565's manual-MNODE leg builder checks for `e.burnState` first and, when present, applies the dv vector in THAT exact recorded state's basis (via `_trajGizmoAxes`) instead of reconstructing from mean-motion phase — so the detached leg's propagated path tracks the ORIGINAL solved leg's real path, not a path departing from a different point on the ring. Re-solving (`missionMnodeResolveToTarget`, 570) deletes the `burnState` stamp — the solver takes over the departure state again, and a later detach re-captures whatever the solver produces this time (never a stale burnState from a previous solve).

Note on the basis itself: `_trajGizmoAxes` builds rHat/vHat/hHat by independently normalizing r and v (NOT Gram-Schmidt-orthogonalized) — exactly invertible (compose→decompose round-trips components, not just magnitude) only when r⊥v (a purely tangential-velocity state, which every `physAimBurnState`-constructed circular parking-orbit state IS by construction). A state with a radial velocity component would make the triad non-orthogonal and the decomposition components would no longer round-trip exactly (magnitude still would, via the orthonormal-in-practice-for-orbital-states triad) — not a concern here since every burnState this pass stamps comes from `physAimBurnState`'s own circular-ring construction.

Gate: 10 new assertions (475 total, up from 465) — `_trajGizmoAxes` right-hand-triad sanity on a synthetic circular state; decomposition against a recorded basis for a mixed pro/rad/nrm case; a TLI-like case (dv purely along the recorded vHat) decomposing to ~pure prograde (|rad|,|nrm| < 1e-6 m/s); and a compose→decompose round-trip identity on a tilted-but-tangential (r⊥v) state.

## 7l. J2 / orbital-economy layer R4 (385/386, 2026-07-10)

Closed-form secular precession from Earth's (and other bodies') oblateness, plus an opt-in integrator term so the effect can be DRAWN on a real propagated orbit, not just quoted as a number.

- **`PROG_BODY_J2`** (385): a data map, not a model — `{Earth: 1.08263e-3, Mars: 1.9555e-3, Moon: 2.033e-4, Venus: 4.458e-6}`. Bodies absent from the map (e.g. Jupiter, Titan) have NO J2 model; callers must treat that as "no data" (functions return `null`), never silently assume zero oblateness.
- **`physJ2NodalRate(aKm, e, iRad, body)`**: standard first-order secular result dΩ/dt = −(3/2)·J2·n·(R/p)²·cos(i), p = a(1−e²), n = √(μ/a³). Sign convention (pinned in the gate): a RETROGRADE orbit (i > 90°, cos i < 0) gets a POSITIVE nodal rate (eastward node regression) — this is what makes sun-synchronous orbits (i ≈ 98°) work, matching Earth's ≈ +0.98565°/day mean heliocentric drift.
- **`physJ2ApsidalRate(aKm, e, iRad, body)`**: dω/dt = (3/4)·J2·n·(R/p)²·(5cos²i − 1) — vanishes at the "critical inclination" i ≈ 63.4° (Molniya's actual design inclination, chosen historically for exactly this reason: an apogee that doesn't drift).
- **`physJ2SunSyncCheck(aKm, e, iRad, body)`**: compares the nodal rate (deg/day) against Earth's mean heliocentric rate 360°/365.2422 days = 0.98565°/day, `sunSync:true` within 0.02°/day. Earth-only by construction (other bodies always report `sunSync:false` — "sun-synchronous" is a specifically Earth-relative launch-planning concept, not exported to Mars/Venus/Moon orbits here).
- **Readout chip** (230-orbit-diagram.js, Define-an-Orbit panel): when inclination is authored and the target orbit resolves, a compact line renders in the mini-diagram's footer — `"J2: node −0.99°/day · apsis +0.12°/day"`, plus an accent-colored `"· sun-synchronous ✓"` when `physJ2SunSyncCheck` passes. Earth-only (the diagram itself is Earth-centric only, per its own header comment) — no chip for escape-mode or other bodies.
- **Optional integrator term** (`physAccel`, 386): `ctx.j2 === true` opts a propagation INTO the J2 acceleration term for its center body (if that body has a `PROG_BODY_J2` entry); DEFAULT OFF — no existing caller sets `ctx.j2`, so this phase is zero behavior change for every currently-shipped propagation (mission legs, shooter, gizmo preview, free-return solve), gate-pinned bit-identical. Form (Vallado sign convention): a_J2 = −(3/2)·J2·μ·R²/r⁵ · [x(1−5z²/r²), y(1−5z²/r²), z(3−5z²/r²)].
- **`ctx.j2` must survive `physPropagateSegment`'s internal ctx rebuild** — the function constructs its own working `ctxNow` per call and only carries forward fields it explicitly lists; `j2` was added to that list alongside `center`/`bodies`/`overrides`/`railFn`/`dtMax` (an easy place for a new ctx field to silently vanish mid-propagation if not threaded through).
- **Pinned in the gate**: 800 km @ 98.6° nodal ≈ +0.9856°/day (within 0.03) and reports sun-synchronous; Molniya (a=26562, e=0.74, i=63.4°) apsidal ≈ 0 (within 0.01°/day); ISS-like 400 km @ 51.6° nodal ≈ −5.0°/day (within 0.3) and NOT sun-synchronous; a body with no J2 entry returns `null` from both rate functions and the sun-sync check; `physAccel` with `ctx.j2` unset/false is bit-identical to the pre-R4 acceleration, `ctx.j2:true` measurably differs; a 5-orbit numerical propagation of the 800 km/98.6° case with `ctx.j2:true` shows RAAN regressing in the sign and rough magnitude the closed-form secular rate predicts (generous 2° tolerance — a coarse trend check, not a precision pin).

## 7m. Body surface rendering + LOD ladder R6.2 (236/574, 2026-07-10)

- **Surface geometry** (`_trajLatLonUnit`, `_trajSpinRotate`, `_trajGeoPolyPath`, `_trajGeoEllipsePath`, `_trajSurfacedDiscSVG`, 574): lat/lon → unit-sphere point in the body's own frame → rotated by the body's spin angle about the WORLD +z (ecliptic-normal) axis → projected through the pass camera (`_trajProj3`, the one projection seam) → scaled to the disc's screen radius. Front-hemisphere only (camera depth ≥ 0); polygon runs break (new subpath) at the limb, same spirit as the existing `viewClampUnits` pattern — filled paths with limb breaks are an accepted rudimentary approximation, not survey-grade cartography.
- **Data source** (236-geo-data.js, new this phase): `PROG_GEO_EARTH` — Natural Earth 110m coastline polygons, Douglas-Peucker simplified, packed as flat integer-tenths-of-a-degree arrays. `PROG_GEO_FEATURES` — Moon maria + Mars regions as `{lat, lon, rLat, rLon, kind}` ellipse approximations from published feature centers (USGS Gazetteer). `PROG_GEO_STYLE` — per-body fill palette, a DATA-palette exemption from the no-chromatic-literals chrome rule (same class as `PROG_BODY_COLORS`, 570). Jupiter/Saturn get no feature data — their bands are procedural lat-strips through the same projection (so they visibly tilt with camera elevation, not a flat texture).
- **Spin angle is a display convention, not a calibrated physical rotation** (`_trajBodySpinAngle`, 574): **Earth** = `2π·viewT_s/86164.1` (sidereal day), **Mars** = `2π·viewT_s/88642.66` (sidereal day) — both with an implicit epoch offset of 0 (NOT tied to any real prime-meridian-at-epoch reference; a Greenwich-facing coastline at viewT=0 is coincidence, not GMST). **Moon**: tidally locked — `progBodyAngleAt('Moon', t) + π`, i.e. the Moon's own Earth-relative orbital position angle (which IS the Earth→Moon direction) plus π, so the nearside meridian (lon 0, where the packed maria live) faces the ACTUAL Moon→Earth direction at every viewT, not a fixed angle. All other bodies: spin angle 0 (no vector surface features are drawn for them, so the angle is unused).
- **Axial tilt is NOT modeled — the single biggest honesty gap of this phase**: every body's spin axis is assumed coincident with the ecliptic normal (`_trajLatLonUnit`'s `+z`). Real axial tilts (Earth 23.4°, Mars 25.2°, others un-modeled here) mean the drawn terminator/pole geometry and the exact limb-crossing latitude of near-polar features are visibly wrong whenever the camera isn't near top-down (`el ≈ 90°`) — acceptable for the "mission-planning flavor" this phase targets, wrong for anything claiming seasonal or lighting accuracy. See critique 55.
- **Limb shading**: one `<radialGradient>` per surfaced-disc instance (unique id per render pass, `_trajGeoIdSeq`), transparent center → ~30–35% black rim (`PROG_GEO_STYLE[body].limb`, a neutral alpha scrim — allowed per the theming exemptions), center offset ~32% of the disc radius toward the Sun's SCREEN direction (a cheap 2D `atan2` between the already-projected Sun and body render positions, not a 3D sun-vector solve) — a rudimentary day-side/terminator cue, not physically-lit shading.
- **Perf clamp**: if the disc's true screen radius exceeds 4× the viewport diagonal (camera deep inside a body, disc mostly off-screen), `_trajSurfacedDiscSVG` skips surface-geometry sampling entirely and emits the base-color fill + limb gradient only — bounds path-string size for the worst-case zoom without a separate viewport-region clip of the lat/lon data itself.
- **Gate** (`tests/math.test.js`, 16 new assertions, 2026-07-10): `_trajLatLonUnit` lands the expected axis points and stays unit-length; `_trajSpinRotate` about +z leaves the pole fixed and rotates the equator correctly; `_trajBodySpinAngle` is monotonic in viewT for Earth/Mars, zero for a body with no vector surface (Venus), and matches `progBodyAngleAt('Moon', t) + π` exactly for the Moon; `_trajTrueBodyRadiusKm` returns the real `PROG_BODIES[body].R` (not the old schematic 3) and the documented Sun constant.

**R6.2 round-4 fixes (574, 2026-07-11)** — three defects found in the round-3 flight test:
- **Exact hemisphere clip, not per-vertex culling** (`_trajHemiClipRuns`, `_trajClippedRunsToPath`): the original approach dropped back-facing vertices and let the SVG fill close the resulting gap with a straight chord through the disc interior — visible pole-on as giant wedges of land color sweeping across the whole disc. The fix clips each polygon (coastlines, maria/region ellipses, gas-giant bands — all three call sites now route through the one clipper) against the front hemisphere (`_trajProj3(...).depth ≥ 0`) and, for every edge that crosses the boundary, interpolates the two endpoint UNIT VECTORS linearly and renormalizes — exact, not approximate, because depth is linear in the input vector, so the interpolated point has depth exactly 0 and therefore lands exactly on the unit circle. Consecutive open runs are stitched with an SVG elliptical arc along the limb (radius `rPx`) instead of a chord; the short-way arc is used when the winding direction is ambiguous (acceptable at coastline/maria polygon scale — the existing disc `clipPath` remains as a second safety net). A real bug surfaced during gate-test authoring: a polygon whose front run straddles the array's start/end seam (dirs[n−1] front, dirs[0] front, connected the "long way" around through the back) got split into a spurious extra fragment by a naive single-pass loop; fixed by splicing the loop-end open run onto the front of `runs[0]` when a wraparound continuation is detected. 5 new gate assertions (front-only/back-only/single-crossing/double-crossing/wraparound-continuity).
- **Stable per-instance ids, not a per-render counter** (defect2): `_trajGeoIdSeq` minted a fresh `<radialGradient>`/`<clipPath>` id every ~33ms rebuild during rotation; since the world layer is swapped wholesale via `innerHTML`, a paint could land between "old ids torn down" and "new ids wired up," reading as a one-frame flicker. Replaced with a deterministic id per body per render instance (`traj-geo-<missionId>-<body>-limb/-clip`) — the wholesale swap now recreates the SAME ids atomically every pass, so no `url(#)` reference ever dangles. Verified stable across 20 synthetic rotation frames (same id string every frame) and non-colliding between Earth and its Moon in the same pass.
- **Real terminator, not a 2D screen-dot offset** (`_trajTerminatorNightPath`, defect3): the limb-shading gradient's day-side offset (unchanged, still a cheap 2D `atan2` cue) made day/night unreadable at a glance. Added an actual terminator: the body→Sun unit vector is now carried as a WORLD-frame 3-vector (`sunDir3`, not a screen angle) all the way into the disc renderer; its camera-projected `depth` component is the orthographic terminator ellipse's minor-axis fraction. Rather than solving the ellipse algebraically, the terminator great circle (parametrized by two world-frame vectors spanning the plane ⊥ `sunDir3`, NOT spin-rotated — illumination depends on sun geometry, not the body's own rotation) is sampled and pushed through the SAME hemisphere clipper coastlines use (doubles as the "ellipse feature" clipper), giving the front-visible terminator arc exactly. That arc plus the correct limb arc (the one that avoids the Sun's own screen angle — the other limb arc is day-side) closes the night region, filled with the existing neutral black-alpha scrim (0.4, allowed exemption) clipped to the disc. Degenerate limits (`|depth| ≥ 0.995`, sun ~directly toward/away from the viewer) are handled explicitly rather than relying on the general formula to degrade gracefully: fully lit emits no scrim at all; fully dark emits a full-disc scrim capped at 0.55 alpha (a soft floor so surface features stay faintly legible, never pitch black). Verified: the terminator tracks Sun-body geometry (near-fixed screen path over a 6h `viewT` scrub, matching Earth's small orbital drift) while land geometry rotates ~90° under it in the same 6h — confirms the terminator does NOT spin with the body, as required.
- **Gate**: 9 new `_trajHemiClipRuns` assertions (tests/math.test.js) bring the suite to 508 total. Perf: 40 synthetic rotation frames at Earth's surfaced-disc LOD tier averaged ~8ms/frame render — well under the 33ms rotate-drag throttle, no observed regression from the added clip/terminator work.

**R6.4 — real textured globes, raster pipeline (574, 2026-07-11)**: replaces the vector surface layer with a RASTER globe (per-pixel equirect sampling) for the 8 bodies with real imagery (`PROG_TEXTURES`, 237-planet-textures.js — Earth/Moon/Mars/Mercury/Venus/Jupiter/Saturn/Uranus/Neptune minus Titan, which has none and keeps the vector/plain path). **Same spin/handedness convention as the vector layer above — not a re-derivation**: `_trajRasterGlobe` derives the exact algebraic INVERSE of `_trajProjectVec` (the one projection seam) plus the inverse of `_trajSpinRotate`, so a texture pixel and a vector coastline pixel land on the identical body-frame lat/lon for the identical screen pixel.
- **Inverse-projection derivation**: forward is `u=-(x·ca-y·sa)`, `v=(x·sa+y·ca)·ct-z·st`, `depth=(x·sa+y·ca)·st+z·ct` (ca/sa = cos/sin(az), ct/st = cos/sin(t), t=π/2−el) on a unit vector — a pure rotation, so `(u,v,depth)` is itself unit-length and `w=+sqrt(1−u²−v²)` recovers the dropped depth on the front hemisphere (r²=u²+v²≤1 test gates the disc edge). Un-tilting `(v,w)` by `−t` gives `ya=v·ct+w·st`, `z=−v·st+w·ct`; un-azimuthing `(xa=−u, ya)` by `−az` gives world `x=xa·ca+ya·sa`, `y=u·sa+ya·ca`; un-spinning `(x,y)` by `−spinAngle` (inverse of `_trajSpinRotate`) gives the body-frame `(bx,by,bz)` that `_trajLatLonUnit` would have produced — `lat=asin(bz)`, `lon=atan2(by,bx)` then index the equirect image (`fx=(lon+π)/2π·w`, `fy=(π/2−lat)/π·h`, bilinear, wrapping X at the seam / clamping Y at the poles).
- **Shading, baked in the same per-pixel loop** (`_trajRasterGlobe`): terminator = dot of the WORLD-frame surface normal `(x,y,z)` (pre-unspin — same as the vector terminator's convention, illumination is independent of the body's own rotation) with the shared `sunDir3` (the identical body→Sun vector `_trajTerminatorNightPath` uses, not re-derived), smoothstepped over a ±0.15 band, floored at 0.45 night brightness so geography stays legible; limb darkening multiplies by `0.75+0.25·w`. Both are approximations of the vector layer's existing gradient/scrim treatment, not new physics.
- **Texture store** (`_trajTextureFor`): lazy per-body singleton — decodes `PROG_TEXTURES[body]` via `Image`, draws to an offscreen ≤1024px sampling canvas, caches its `ImageData`. Decode is async; every call site checks `.ready` and falls back to the existing vector `_trajSurfacedDiscSVG` path until `onload` fires, which invalidates the raster dataURL cache and calls `_trajRequestRepaint()` (re-renders every mounted `.traj-wrap` at its current camera through the same `_trajWorldSVG` rebuild `_trajApplyCam` uses) so the swap to real imagery happens without waiting for the next user gesture.
- **Integration** (`_trajBodyDiscTiered`): at the surfaced-disc tier (`r ≥ _TRAJ_FEATURE_PX`, 14px — same threshold the vector layer already used to gate feature sampling), if a ready texture exists for the body, the vector base/features/terminator/limb stack is fully REPLACED (no double-draw) by an `<image>` element pointing at a cached raster `canvas.toDataURL('image/png')`, sized/positioned to the disc in world-layer coordinates. Canvas render size is `min(2·discPx, 512)` — SVG upscales beyond that, cheaper and visually indistinguishable at this LOD.
- **Cache/throttle**: `_trajRasteredDiscDataURL` keys on `(body, discPx bucketed to 8px, spin quantized to 0.01 rad, az/el quantized to 0.01 rad, sunDir3 quantized to 0.1 per axis)` and additionally throttles ANY re-raster of a given body to at most once per ~120ms, reusing the most recent dataURL in between — during a rotate-drag (which re-renders at the existing ~33ms cadence) this means several frames in a row can show a very slightly stale globe orientation; acceptable per the brief, same spirit as the existing rotate throttle.
- **Perf**: 512px raster measured ~9–13ms per call (typed ImageData in/out, no per-pixel canvas API calls) — under the 120ms re-raster budget and the panel stays interactive during drag since cached frames are reused between throttle windows.
- **Gate**: the inverse-projection math (`_trajRasterGlobe`'s coordinate transform) is exercised indirectly by the existing `_trajLatLonUnit`/`_trajSpinRotate`/`_trajProjectVec` assertions (§7m/§7o) — those three primitives are literally what the inverse re-derives algebraically, so no new vm-testable pure function was extracted; the raster loop itself is canvas/DOM-bound (`ImageData`, `Image`, `document.createElement('canvas')`) and was instead verified by browser pixel-sampling (known-geography color checks — Sahara/Pacific/Amazon — at a fixed camera) during manual verification, not the Node gate.

**R6.5 — apoapsis/periapsis markers + trajectory occlusion by opaque bodies (574, 2026-07-11)**: two presentation-layer additions, zero ΔV/physics consequence (rendering-only; `dvExpended` golden unchanged).

- **Apse markers** (`_trajApsePoints`, pure — samples `progOrbitSamplePoints` and picks the periapsis/apoapsis POINT by actual radius magnitude, not by blindly trusting `sample[0]`/`sample[N/2]`): every drawn orbit ring — heliocentric planet rings, moon rings, and mission orbit rings — gets a small filled-triangle "Pe"/"Ap" glyph plus a distance label at its true apsides, registered through the existing overlay label registry (`_trajRegisterLabel`, same LOD/collision system as every other ring label — fades and de-clutters with its parent ring). Distance format differs by ring class: heliocentric rings show **AU** (`_trajFmtApseDist(km,'au')`); Moon-class rings show **raw center-to-body km** (`'km'` mode — e.g. the Moon's own orbit around Earth reads Pe≈363,296 km / Ap≈405,504 km, matching the well-known lunar perigee/apogee); mission rings reuse the ring record's OWN `peri`/`apo` fields directly, which are already **altitude above the body's surface** (not center-distance) by construction (see the `rp = R + peri` convention above) — no separate computation needed there. Markers inherit the ring's own stroke color (no chromatic literal) and are individually skipped if their own point fails the occlusion test below (one apse can be visible while the other is hidden behind the body).
- **Trajectory occlusion by opaque bodies**: orbit rings AND physics-leg polylines (`_trajPolylineSVG`, used by every `_trajPhysLegRender` call site — MNODE vector-burn legs, converged interplanetary/local transfer legs) are now clipped where they pass behind an opaque body disc drawn in the SAME frame — a LEO ring's far side hides behind Earth's disc, which is the correct/desired reading (not a bug to avoid). Schematic (unconverged) Hohmann-arc legs and SOI escape/capture spurs are **out of scope** for this pass — the brief's literal wording covers rings and physics-leg polylines only; those two schematic-geometry emitters are noted here as a known gap, not silently addressed.
  - **Depth-sign convention (derived, not assumed — verified empirically in-browser before coding)**: the painter sort in `_trajWorldSVG` is `records.sort((a,b) => a.depth - b.depth)`, drawn ascending — so a LARGER `depth` (the camera-axis component from `_trajProj3`) is drawn LATER, i.e. NEARER the camera. Empirical check (top-down camera, `az=0, el=π/2`, where `depth` reduces to world `z` by construction): a body at the origin with `R=1000` has its near cap at `depth=+1000`; a synthetic point at `z=+1500` (beyond the near cap, toward the camera) tests as NOT occluded, and a point at `z=−1500` (behind the body along the same sightline) tests as occluded — confirming larger depth = nearer camera, matching the painter-sort direction. Printed in the verification transcript.
  - **Occlusion predicate** (`_trajPointOccluded`, pure): for an opaque body disc `{cx,cy,depth,R}` (render-unit center, real-km camera-axis depth, real-km physical radius) and a candidate point `(px,py,pdepth)`, the perpendicular screen offset in real km is `ρ = hypot(px−cx, py−cy) / zoom`. The body's NEAR cap (the point on its surface closest to the camera at that radial offset) sits at `depth + sqrt(R²−ρ²)`. The point is occluded iff `ρ < R` (inside the disc's silhouette) AND `pdepth < nearCapDepth` — i.e. it's behind the visible sphere surface along that sightline. A point far behind the body (beyond the far cap) is still correctly occluded — the sphere is opaque, so anything directly behind it along the sightline is hidden regardless of how far back it is.
  - **Depth threading**: every ring/leg point's depth is computed in the SAME real-km, camera-relative convention as the painter sort — `centerDepth + localOffsetDepth`, where `centerDepth` is the ring/leg's own primary body's `toRender(...).depth` (threaded as `oDepth` through `_trajBodyFrameContent` → `_trajRingSVG`'s `opts.centerDepth` and → `_trajPhysLegRender`'s `anchorOf` closures, which now return `{x,y,depth}` instead of `{x,y}`), and `localOffsetDepth` is the UNSCALED `_trajProj3(...).depth` of the sample's local offset vector (exact because the projection is a pure rotation — linear, so depth scales/adds exactly, no approximation). Call sites that haven't threaded `oDepth` default to `Infinity` ("never occluded") — backward-compatible, not a silent correctness bug.
  - **Order-independence**: which bodies occlude a given frame's content is decided by a PRE-PASS at the top of `_trajWorldSVG` that collects every body (Sun excluded — its glyph is a fixed schematic marker, never a true-scale rendered disc) whose apparent screen radius clears the disc-tier threshold (`trueRpx ≥ _TRAJ_FEATURE_PX`, the same 14px threshold the surfaced-disc renderer already uses to decide "worth sampling features for") into a single `_trajOccludeBodies` list BEFORE any ring/leg content is emitted — so occlusion tests are independent of body iteration order (a Mars-frame ring occluded by a body drawn later in `Object.keys(PROG_HELIO_R)` iteration order still sees it).
  - **Run-splitting**: `_trajOcclusionSplitRuns` drops occluded samples and breaks the polyline at the crossing (same "drop + break" pattern as `_trajHemiClipRuns`/`viewClampUnits` elsewhere in this file) — exact limb interpolation is deliberately NOT done at ring/leg sample density (96/64 samples respectively), noted here per the brief's explicit allowance. A closed ring therefore is NOT wraparound-stitched across its own start/end seam when occlusion splits it (unlike `_trajHemiClipRuns`, which does stitch coastline polygons) — a visually continuous visible arc that happens to straddle sample index 0 can render as two adjacent fragments instead of one; cosmetically minor, not a correctness bug, and cheap to fix later if it reads as a seam in practice.

## 7o. World-view handedness fix — screen-y mirror bug R6.3' (574, 2026-07-11)

**Convention, stated once so this never regresses silently**: every world-frame vector in this program (heliocentric/planetocentric position from `progBodyEphemState`/`physElementsToState`, and the surface lat/lon → unit-sphere mapping `_trajLatLonUnit`) uses the standard right-handed ecliptic frame — `+z` = ecliptic north, reference direction `+x`, and angles increase **counterclockwise** as seen from `+z` looking down (i.e. `+x → +y` is the positive-angle sense: prograde orbital motion and increasing east longitude both go this way). This is a math convention (x-right, y-UP).

**The bug**: `_trajProjectVec` (130) — the ONE seam every world-space consumer routes through (surface points via `_trajSurfacePoint`, orbit rings, the maneuver gizmo, hover rails, ring-direction tangents, the site marker/mock-ascent pipeline) — mapped world `(x,y)` straight to screen `(u,v)` with `v = y` at the default top-down camera (`el = π/2, az = 0`). SVG screen space is **y-DOWN**. Plotting world-`y` directly onto a y-down screen is a reflection across the x-axis, not a rotation: it flips chirality. Effect was system-wide because it's one shared seam:
  - **Geography mirrored**: Australia rendered LEFT of Asia (correct CCW-from-north order is Europe → Asia → Australia → Pacific → Americas; the bug reversed it).
  - **Orbital motion mirrored**: real prograde motion (CCW from ecliptic north) rendered as clockwise on screen.
  - Everything downstream (site marker/Florida placement, gizmo prograde-handle direction, ring direction-of-motion fade, hover-ball tracking) inherited the same mirror because none of them duplicate the y-mapping — they all call `_trajProj3`/`_trajSurfacePoint`, which call `_trajProjectVec`.

**The fix (R6.3b, corrected same day)**: a det=−1 reflection is needed, and there are two candidates — negate screen-y or negate screen-x — which differ from each other by a 180° screen rotation. The FIRST attempt negated screen-y (`v = −(ya·ct − z·st)`); that repairs chirality but flips the tilt term's sign with it, so at tilted views (`el < π/2`) the NORTH pole projected toward the BOTTOM of the screen — the user immediately read the world as "flipped 180°". The correct reflection negates screen-**x**: `u = −xa`, `v = ya·ct − z·st` (original v restored). Chirality is fixed (east longitudes/prograde motion read CCW at the top-down view) AND north stays up: world `+z` contributes `v = −z·st`, negative = up-screen in SVG's y-down space. `depth` is untouched. Because every consumer is downstream of this one function, the fix is global and self-consistent by construction; no other file needed a compensating change.

**Gate impact**: the R2 projection-identity goldens (§ R2 block, `tests/math.test.js`) are pinned to `_trajProjectVec`'s literal output and were re-derived for the final mapping (`el=90`: u=−x, v=+y; `el=0` edge-on: v=−z i.e. north up-screen; `az=90`: +x → v=+1). Pure-angle goldens that don't touch the projection function (`progLaunchRaanFor` §7n, `progOrbitSamplePoints`'s radius/closure checks, hemisphere-clip depth tests) are untouched — they operate on world-frame vectors or camera-depth, never on the flipped screen axis.

**Not touched**: `_trajWorldToScreen` (622) — the render-space → overlay-px affine map used by labels/markers — has no independent y-mapping of its own; it linearly scales/translates whatever `_trajProj3` already produced, so it inherits the fix automatically and needed no edit.

## 7p. Launch-to-destination planner — pure math, phase 1 (415, R7, 2026-07-11)

Given a launch body, a destination, and an epoch, computes the IDEAL parking orbit (inclination, LAN, altitude) that sets up the lowest-ΔV departure toward that destination, plus the launch azimuth and departure C3. Pure functions only (`415-launch-planner.js`), no UI wiring yet (that is a separate later step) — this phase is the math core plus its gate tests.

- **3-D Lambert (`progLambert3D`)**: `progLambert2D` (410) is explicitly 2-D — it projects heliocentric positions to the ecliptic (z dropped) because a genuine v∞ VECTOR (needed for declination-of-launch-asymptote math) can't come out of a planar solve. `progLambert3D` ports the identical universal-variable algorithm (Curtis §5.3, bisection on ψ — same algorithm 410 already cites) to 3 dimensions: every step is dimension-generic (dot products, vector scale/add via 385's `physV3`/`physSub`/`physDot`/`physCross`/`physMag` helpers) EXCEPT the prograde/retrograde disambiguation, which mirrors 410's existing convention exactly — sign of the z-component of `r1 × r2` stands in for "which way is prograde," valid because every body in `PROG_BODY_ELEMENTS` has small ecliptic inclination (Mars 1.85°, Venus 3.39° — same basis as critique 42).
- **`progDepartVinf(fromBody, destBody, tDepartJD, tArrJD)`**: positions/velocities via `progBodyEphemState` (360, the ONE position source) at the two dates; `vInf = Lambert departure velocity − fromBody's heliocentric velocity at departure`; `c3 = |vInf|²`.
- **`progOptimalDeparture(fromBody, destBody, epochJD, opts)`**: scans a (departure day × TOF) grid for the minimum-C3 solution — minimizing C3 for a fixed parking altitude is equivalent to minimizing the departure burn, so "lowest ΔV" and "lowest C3" are the same optimization here. Per-destination default windows (`_LP_DEFAULT_WINDOWS`, 415) are hand-picked from rough synodic periods (Mars ~780 d, Venus ~584 d) and typical Hohmann-class TOF ranges — NOT derived from a synodic-period formula in code, same "hand-tuned constant" category as critiques 7/24/51/52/53. An explicit `{tDepartJD, tArrJD}` pair in `opts` skips the scan entirely. Measured (Mars, epoch 2026-07-09, default window, ~2,425 grid evaluations): **99 ms**, optimum at TOF ≈ 294 d, C3 ≈ 9.15 km²/s², v∞ ≈ 3.025 km/s.
- **`progIdealParkingOrbit({vInfVec, siteLatDeg, altKm})`**: DLA (declination of the launch asymptote) = `asin(vInf_z / |vInf|)`, computed in the ECLIPTIC frame — i.e. treating the ecliptic as a stand-in for the launch body's equatorial plane, the SAME no-axial-tilt approximation already documented for the surface renderer (critiques 54/55; Earth's real ecliptic-vs-equatorial obliquity is 23.4°). Ideal inclination = `max(|DLA|, |siteLat|)`; when `|DLA| < |siteLat|` the site physically cannot reach `inc = |DLA|` without a dogleg, so inc is pinned to `|siteLat|` and `planePenalty = |siteLat| − |DLA|` is reported (with an explanatory `note`). LAN is chosen so the parking plane's normal is perpendicular to vInf: `Ω = α − asin(tan(DLA)/tan(inc))` where `α = atan2(vInf_y, vInf_x)` is the asymptote's right ascension — derived directly from the plane-normal dot-product condition `n(inc,Ω)·vInf = 0` with `n = [sin(Ω)sin(i), −cos(Ω)sin(i), cos(i)]` (the same normal convention `progOrbitSamplePoints`'s rotation matrix implies), verified to residual ~1e-16 in the gate (not just "close," exact to floating-point). The supplementary root (`Ω − 180° − asin(...)`, same plane's descending node) is not returned separately — a plane has one normal up to sign, so it's the same physical orbit. `inc ≈ 0` (equatorial/ecliptic-plane parking) is a degenerate case where the ascending node is undefined; LAN is pinned to 0 with a note rather than propagating a 0/0. Azimuth is `progLaunchAzimuthDeg(siteLatDeg, inc_deg)` (360, unmodified, direct reuse).
- **`progPlanLaunchToDestination({fromBody, destBody, epochJD, siteLatDeg, altKm, tDepartJD?, tArrJD?})`**: orchestrates the above. Three destination shapes: (a) a planet name string → full scan/Lambert/DLA path; (b) an Earth-orbit target spec `{inc, lan, alt}` → short-circuits to "ideal parking = coplanar with the target," `c3`/`vInf` = 0 (no departure hyperbola for a same-body destination); (c) `'Moon'` → **phase 2 (2026-07-14, user feedback item 1)**: routed through the GEOCENTRIC cislunar plane math instead of the heliocentric Lambert scan (a lunar transfer isn't a heliocentric departure at all, so `progOptimalDeparture` never applied) — see `progMoonPlaneAt` below. `dvDepart` reuses the existing `progDvTLI(altKm)` (360) so the readout matches what the mission's actual TLI burn costs; `c3`/`vInfMag`/`dla_deg`/`tArrJD` stay `null` (no departure hyperbola in a patched-conic geocentric transfer).
- **`progMoonPlaneAt(epochJD, t_s)`** (415, phase 2): the Moon's INSTANTANEOUS orbital-plane inclination/LAN in the program's ecliptic reference frame, from the orbit-normal vector `h = r × v` of `progBodyLocalEphemState('Moon', t_s)` (the Earth-centered, parent-relative state — before Earth's own heliocentric position is added back in by `progBodyEphemState`). `inc = acos(h_z/|h|)`, `LAN = atan2(h_x, −h_y)` (node vector `N = k × h`) — the standard orbital-elements-from-state-vector identity, same family as `physStateToElements` (385) but kept local to 415 since it only needs the two angles, not a full element set. `progPlanLaunchToDestination`'s Moon branch treats "ideal parking" as coplanar with this plane (minimizes the TLI→LOI plane-change cost — a real free-return trade exists but isn't modeled here, see critique 58 below).
- **`progResolvePlaneTarget(target, epochJD, t_s, siteLatDeg)`** (415, user feedback item 2 — "launch into the plane of X"): generic resolver behind the launch card's "Match plane" picker. `target === 'Moon'` → `progMoonPlaneAt`; a catalog reference-orbit object `{inc, lan, name}` → its own inc/lan pass through unchanged. Returns `{inc_deg, lan_deg, source, unreachable, penalty_deg}` — `unreachable`/`penalty_deg` are computed (`|siteLat| > inc`) but never clamp the values; the UI surfaces the warning instead (same "everything user-overridable, nothing silently fixed up" philosophy as R7 phase 1).
- **Gate** (`tests/math.test.js`, 2026-07-11, 36 assertions; +8 phase-2 assertions 2026-07-14): DLA exact for in-plane and tilted vInf; `inc = max(|DLA|, lat)` pinned at two hand-picked cases (23°/28.5° → 28.5°, penalty 5.5°; 40°/28.5° → 40°, penalty 0); the plane-contains-vInf invariant checked across 5 vInf directions × 4 site latitudes (20 cases, residual < 1e-6); azimuth ties to `progLaunchAzimuthDeg` directly; a real Mars `progOptimalDeparture` run asserts C3 in a loose 4–30 km²/s² sanity band and TOF in 150–350 d (not a pinned magic number — printed, not asserted exactly) plus its own plane·vInf residual; Earth-orbit short-circuit. Phase 2: Moon plan returns real numeric inc/lan (not deferred) with inc in the plausible [18°,29°] lunar-plane-oscillation band and `dvDepart` matching `progDvTLI`; `progMoonPlaneAt` inc/lan range sanity; `progResolvePlaneTarget` Moon-target agreement with `progMoonPlaneAt` directly, an unreachable-flagged high-latitude case, and a pass-through catalog-object case.

## 7s. MISSION_MODEL_V2 Phase 4 — NRHO periodicity corrector + propagated ring (425/566/570/574/5746, 2026-07-14)

**U1 — periodicity corrector, run OFFLINE (node+vm smoke, not shipped as a runtime function).** FD-Jacobian Newton over 3 free params `[vx, vy, P]` (perilune in-plane velocity components + period), minimizing one-rev position closure `|r(t0+P) - r(t0)|` via `physPropagateSegment` in the REAL ephemeris model (`ctx = {center:'Moon', bodies:['Moon','Earth','Sun']}`, no CR3BP rotating frame). Damped Newton acceptance (halve the step while the miss doesn't shrink), same discipline as `physShootToTarget` (565) — a small hand-written variant was used rather than that exact function since periodicity-closure (state(t0+P) vs state(t0)) isn't a burn-solve/target-miss shape.

**Seed family scanned, HONEST result.** Seed convention per the task: perilune on the south pole in ecliptic-z (`r0 = [0,0,-rp]`), velocity in the ecliptic xy-plane so the orbit plane contains z (`v0 = [vp,0,0]`), vis-viva-ish `vp` guess about the Moon alone. The LITERAL canonical 9:2 NRHO (rp≈3,400 km, ra≈70,000 km, P≈6.56 d) does **not** converge in this integrator: that apolune sits outside the Moon's own SOI (~66,100 km per `physSoiRadius`) — the real 9:2 NRHO's outer arc is a near-rectilinear excursion toward L2 that depends on being IN a rotating Earth-Moon frame near the L2 libration point, which this restricted-3-body / SOI-patched integrator doesn't model as "still gravitationally with the Moon." Seeded there, the trajectory drifts and exits the Moon's SOI within ~8 days rather than closing.

A lower-apolune family member DOES converge cleanly and stays inside the SOI the whole rev:
- rp = 3,000 km, ra = 60,000 km → seed `v0 = [1.764338088034402, 0, 0]` km/s
- Corrected period **P = 406,944 s = 4.71 days** (seed guess needed no Newton iterations — it was already under tolerance: `iters:0`)
- **One-rev position closure = 468.6 km** (< 500 km acceptance, §14 U1/U4)

## 7x. MISSION_MODEL_V2 §17 N3 — switchable reference frames, live rendering transform (574/425, 2026-07-14)

**The transform.** A frame is a time-dependent orthonormal basis B(t) (columns = frame axes, world-aligned). For any world-axis-aligned vector `pRel` at its own epoch `t` (a trajectory sample's real time, or "now"/`viewT` for a body/marker/spin-baked surface point), the renderer computes

```
q(t) = B(t)^T . pRel(t)          — 574's _trajFrameTransform(frameKind, body, pRel, t)
```

i.e. `pRel` expressed IN FRAME COORDINATES at its own epoch, fed **directly** to the camera projector (`_trajProjectVec`/`_trajProj3`) — no re-expansion back to world/inertial axes. `inertial` returns `B = null` and the caller short-circuits to the untouched vector (zero overhead, byte-identical to pre-N3 rendering).

**Az convention (the practical requirement the spec asked to be documented): the frame rotates the WORLD, the camera stays put.** Because `q(t)` is fed straight into the az/el projector, the projector's az/el are effectively rotating the FRAME's own axes, not fixed ecliptic-world axes, whenever a non-inertial frame is selected. Switching frames never jump-cuts the anchor body (it renders at the camera's floating-origin center, untouched by this seam either way) — but everything ELSE re-orients under the new frame's basis, which is the whole point (a rotating-frame-periodic loop only closes when viewed this way).

**Deviation from the literal MISSION_MODEL_V2 §17 N3 wording — documented, not hidden (retires the "half-fix" risk, see critique 70).** The spec text describes the formula as `q(t) = B(viewT)·B(t)ᵀ·pRel(t)` (de-rotate to frame coords at the sample's own time, then RE-EXPAND into world axes at the CURRENT view epoch) and states "bodies/markers/event nodes at viewT (transform is identity at t=viewT — verify that means bodies need NO code change)". Both claims are true only for the **inertial** frame. For any non-inertial frame, `B(viewT)·B(viewT)ᵀ = I` **always** (elementary orthonormal-matrix algebra) — so literally implementing the spec's own formula makes EVERY point rendered at `t=viewT` (which is every body/marker glyph, always) come out **byte-identical to its raw inertial position**, regardless of frame — the Moon would NOT render fixed in the Earth-Moon frame, and the whole feature would be visually inert for anything except historical trajectory samples. This was caught by deriving the tautology directly (Moon's frame-coordinates at its own epoch are trivially `(d,0,0)` **by construction**, since the EM frame's x-axis IS DEFINED as the Earth→Moon direction at that instant — re-expanding via `B(viewT)` just undoes that and hands back the raw vector). Dropping the outer `B(viewT)·` re-expansion (i.e. rendering directly in frame coordinates, as above) is what actually makes the Moon render frame-fixed, the NRHO ring close live, and body-fixed globes stop spinning — all three are exercised by the gate and by browser verification. The spec's own gate-test wording item "(3) t===viewT ⇒ identity" is reinterpreted in the actual test (`tests/math.test.js` "N3:" block) as **magnitude preservation under rotation** (`|q(t)| === |pRel|` for every frame/epoch) — a real, verifiable invariant — rather than literal identity, which only holds for `inertial`.

**Frame definitions:**
- `inertial` — default, today's rendering. `B = null`.
- `body-fixed` — `B(t)` = rotation about the anchor body's spin axis (+z, ecliptic-normal) by `_trajBodySpinAngle(body, t)` — the SAME spin source the raster/vector globes already use. Because a surface feature's world direction is `_trajSpinRotate(localDir, spin(t))` (i.e. `R(spin(t))·localDir`, already baked in before it reaches the projector) and `B(t) = R(spin(t))`, calling `_trajProj3` on that world direction with `t=viewT` (the default — surface points are always drawn "now") gives `B(viewT)ᵀ·R(spin(viewT))·localDir = localDir` **exactly**, independent of viewT: the globe stops rotating on screen for free, no special-casing needed anywhere in the surface/raster path (verified — raster cache key, which is keyed on the same `spin` variable fed into `_trajRasteredDiscDataURL`, is now constant across a viewT scrub when body-fixed is active on that body).
- `earth-moon-rotating` — `B(t)` from `_refRotBasisPair('Earth','Moon',t)` (425; `_refEmRotBasis` is now a 1-line alias of this generalized pair function — same math as the N2 wrap/harness, unchanged behavior there). `xh` points from Earth toward the Moon.
- `sun-earth-rotating` — `_refRotBasisPair('Sun','Earth',t)`, same construction.

**Seams (the four consumer categories from the spec):**
(a) **Polyline samples** (physics legs, `_trajPolylineSVG`) — each sample projected with `t = s.t` (its own true epoch). (b) **Ring samples** — the propagated NRHO/libration rings (`_trajPropagatedRingSVG`) switch, when a non-inertial frame is active, from the existing seed-epoch-rebased `refOrbitSamplePropagated` (which freezes the shape at t0 — critique 64) to a new **raw**, un-rebased sample source (`refOrbitSamplePropagatedRaw`, 425 — same propagation, no rotating-frame re-base), each point transformed at its own `s.t`. This is what closes the ring LIVE at any `viewT` and retires critique 64 for any consumer that opts into a non-inertial frame; **the inertial frame deliberately keeps the old rebased path untouched** (zero regression — same seed-epoch-frozen shape as before N3, per the spec's own "decide and document" instruction). (c) **Bodies/markers/event nodes** — drawn at `t=viewT` (the `_trajProj3` default when no epoch is threaded) — NOT an identity no-op except for `inertial` (see the deviation note above); this is what makes the Moon render frame-fixed in the EM frame. (d) **Launch site / surface features** — already spin-aware via `_trajBodySpinAngle`; composes correctly with `body-fixed` per the derivation above, verified in-browser (raster cache key constant across scrub).

**Occlusion/LOD/labels** consume the already-projected `(x,y,depth)` output of `_trajProj3` exactly as before — the frame transform is fully upstream of that pipeline, so occlusion (a globe hiding the far arc of its own ring) and LOD/label gating ride automatically with no code changes, verified in the EM-rotating + Moon-anchor browser check.

**Persistence:** frame choice is per-mission transient view state (`_trajFrameByMission`, sibling of `_trajCamByMission`), **not** session-persisted — the camera itself isn't persisted either (checked 455-autosave.js; no `_trajCamByMission` hook exists), so frame choice matches that existing pattern rather than introducing a new one.

## 7y. MISSION_MODEL_V2 §19 E1 — electric propulsion / low-thrust physics substrate (386, 2026-07-14)

**Scope: E1 only — pure physics + gate. No event kind, no vehicle model, no UI (that's E2/E3).** `physPropagateSegment` gains an opt-in thrust term via `ctx.thrust = { thrust_N, isp_s, m0_kg, law, coastWindows?, mDry_kg? }`.

**Model.** Two coupled ODEs ride the SAME leapfrog (kick-drift-kick) scheme 386 already uses for r,v — not an Euler bolt-on:
- **Acceleration**: `a = a_gravity(r,t) + (T/m)·û(law)`, where `T/m` is computed in N and kg (m/s²) then divided by 1000 to match the integrator's km/s² units — the one unit conversion in the whole model, done once in `physAccelWithThrust`.
- **Mass**: `ṁ = −T/(Isp·g₀)` (g₀ = 9.80665 m/s², `PHYS_G0_MS2`), a CONSTANT rate whenever thrust is active — the segment ODE is exactly linear in t over a step, so it is integrated **analytically per step** (`physMassBurn`: `mEnd = mStart − rate·dt`, clamped to `mDry_kg`, default 0) rather than approximated. This is exact regardless of step size, and it is what makes deliverable 2 below exact rather than approximate.

**Velocity-dependent force in a kick-drift-kick scheme.** `prograde`/`retrograde` steering depends on the INSTANTANEOUS velocity, which leapfrog doesn't have mid-step by construction (it has `v` at t and the half-kicked `vHalf`). `physLeapfrogStepThrust` uses `state.v` (start-of-step) for the first kick's thrust direction and the drifted `vHalf` (a same-step estimate of v at t+dt) for the second kick's — the same half-step-velocity approximation the scheme already makes for r via `vHalf`, just extended to the direction vector. Documented approximation, not exact for a curving velocity vector within one step; bounded by the step-control rule below (§7y step rule) keeping the per-step direction change small.

**Steering laws v1** (`physThrustDir(law, r, v, t)`): `prograde` = `+v̂`, `retrograde` = `−v̂`. Dispatch is a plain function so `normal`/Q-law slot in later without touching the integrator. **Unknown law → no thrust at all** (`physThrustLawKnown`): no acceleration AND no propellant burn — a genuinely idle engine, not a thrust-less burn (that would be a mass-accounting lie). Never throws mid-integration; the gate exercises this explicitly.

**Ballistic byte-identity.** `hasThrust = !!ctx.thrust` is hoisted ONCE per `physPropagateSegment` call; every branch below it (`physLeapfrogStep` vs `physLeapfrogStepThrust`, the `raw` sample shape with/without `m`/`dv` fields, the returned object with/without `dvAccum`/`propDepleted`) is a plain `if/else` on that boolean — the no-thrust path calls the SAME `physLeapfrogStep`/`physAccel` as before E1, with no new fields attached to any object. Gate-pinned against the existing N1 continuity golden: **413 steps, unchanged**, plus an explicit check that no thrust field (`dvAccum`, `propDepleted`, `stateF.m`) leaks onto a no-thrust result.

**Step control (the new dt rule).** While thrust is active (law known, not inside a coast window, not depleted), `dt` is additionally capped at `period(local)/40` (`PHYS_THRUST_REVS_RESOLUTION = 40`), composed with the existing distance-based ladder via `Math.min()` — NOT quantized onto `PHYS_DT_LADDER` (the cap is a continuous cap, not a ladder rung; still fully deterministic, just not power-of-2 snapped). `period(local) = 2π√(|r|³/μ_center)`, the same formula `physStepFor` already uses internally, exposed as `physLocalPeriod`. Measured: a 1-day LEO burn (T=50 N, m0=1000 kg) at 300 km altitude has period 5,422.5 s (period/40 = 135.6 s) and averaged 25.9 s/step over 3,331 steps — well under the cap (the distance ladder was already finer than period/40 at LEO altitudes; the cap matters for higher/slower orbits where the ladder would otherwise coarsen past what a thrust arc needs to resolve a rev cleanly).

**Depletion guard.** `mDry_kg` (default 0) is a hard floor; `physMassBurn` clips consumption to `mStart − mDry_kg` and reports `depleted:true` for that step, which the caller latches (`propDepleted` on the result) — subsequent steps see `active=false` regardless of coast windows, thrust cuts off exactly at the floor, and the ballistic path continues unmodified to `tMax`. Mass never goes negative by construction (the clip, not a post-hoc `Math.max`).

**Coast windows.** `coastWindows: [[tStart,tEnd], ...]`, MET-relative (relative to the segment's own `t0`, i.e. checked against `t - t0`), simple half-open interval containment (`physThrustWindowActive`) — v1, no partial-step interpolation at a window boundary (a step whose start sits inside/outside a window uses that classification for the whole step; boundary steps are therefore a few-second-scale approximation, immaterial at the day-to-month timescales this model targets).

**Edelbaum planar comparison (measured 2026-07-14).** LEO 300 km → 1,000 km circular, planar (`Δv = |v₀−v₁|`, the `Δi=0` reduction of the general circular-to-circular Edelbaum formula), Earth-only body list, T=5 N / Isp=2,000 s / m0=500 kg (chosen to keep the gate fast — see the runtime note below): integrated `dvAccum` sampled at the first sample crossing the target radius vs the analytic Edelbaum value:

| Thrust | Edelbaum Δv | Integrated Δv (at crossing) | Ratio |
|---|---|---|---|
| 3 N | 0.37620 km/s | 0.37425 km/s | 0.9948 |
| 5 N | 0.37620 km/s | 0.37973 km/s | **1.0094** (gate-pinned) |
| 8 N | 0.37620 km/s | 0.37358 km/s | 0.9931 |

All three sit inside the spec's documented ~1–3% band (Edelbaum assumes constant acceleration and a quasi-circular spiral; the integrated case depletes mass — accel actually increases slightly over the burn — and "first sample at/past the target radius" adds a little slop on top of the true crossing point). Gate pins the 5 N case at <3% with the measured 0.94% written into the assertion label.

**Energy audit (measured 2026-07-14, independent of Edelbaum's assumptions — pure work-energy truth).** 1-day prograde burn, T=5 N/Isp=2,000 s/m0=500 kg, LEO 300 km, sampled hourly (24 chunked re-propagations so v and m are available at each sample — the base `physPropagateSegment` only exposes m/dv on samples, not v, in v1): `ΔE_actual` (osculating specific energy, final − initial) vs `∫a_T·|v| dt` (trapezoidal over the 24 hourly samples) agree to **0.015%** (ratio 1.000149). Gate pins <1% (60× headroom over the measured residual, which is pure trapezoidal quadrature error against the leapfrog's own finer internal steps).

**Mass-coupling exactness (measured 2026-07-14).** 3-day burn, T=50 N/Isp=2,000 s/m0=1,000 kg (Earth-only, deliberately unrealistic dynamically — escapes within the window — because this assertion is about the mass ODE, not the trajectory): `dvAccum = 21.20383930 km/s` vs `Isp·g₀·ln(m0/mF)/1000 = 21.20383930 km/s`, diff `6.75e-14` (float noise from ~3,472 accumulated log-sum steps telescoping to the same value as one direct log). This is not a "close enough" check — the per-step analytic mass integration makes the two expressions the SAME sum-of-logs telescoping to `ln(m0/mF)`, so the gate asserts near-equality (`1e-9` tolerance) rather than a physically-motivated band.

**Runtime note (why the gate uses N-scale thrust on kg-scale masses instead of mN-scale thrust on a real SEP stage over months).** A real electric-propulsion mission (mN thrust, months of continuous burn) needs 10⁵–10⁶ integrator steps per the spec's own estimate — seconds-scale per run, which is exactly why MISSION_MODEL_V2 §19's E2/E3 put the real computation behind an explicit "Compute trajectory" button with a progress bar rather than inside the synchronous gate. For E1's gate (budget ~15 s for the whole new block), thrust is scaled UP by orders of magnitude on a small test mass instead — a few newtons on a few-hundred-kg body reaches the same Δv/energy regime a mN engine reaches over months, in <15,000 steps and well under 150 ms wall-clock per case (measured: the 5 N Edelbaum case ran in ~100 ms across 3 thrust levels). The physics being validated (the mass ODE, the acceleration term, the step cap) doesn't care about absolute thrust magnitude — only the ratios (T/m, T/(Isp·g0)) matter for these invariants, so this substitution is physically honest, not a shortcut around the model.

**Critiques (new):**
72. **The half-step-velocity approximation for steering direction is not exact for a curving velocity vector.** `physLeapfrogStepThrust` uses `state.v` at step-start for the first kick's thrust direction and the drifted `vHalf` for the second — consistent with how leapfrog already treats r, but not a rigorous mid-step velocity. Bounded by the period/40 step cap (small angular change per step at that resolution); a future accuracy pass could re-evaluate `û` from a corrected end-of-step velocity estimate (implicit / iterated leapfrog), same spirit as §7u's "future accuracy pass" note for the dt ladder.
73. **Coast-window boundaries are step-granular, not interpolated.** A step whose `[t, t+dt)` interval straddles a coast-window edge uses the classification (`active`/coasting) of the interval's start time for the whole step — a sub-step time slice of error at the boundary, immaterial at the day-to-month timescale of any real low-thrust leg but worth documenting before E2 authors duration/coast fields that a user might set to second-level precision.
74. **Edelbaum's assumptions, restated as the boundary of what the gate validates.** The comparison above assumes: constant acceleration (ours decreases the exhaust-velocity term as mass drops — small effect, dominant fraction of the measured 0.94-3% spread is depletion-driven, not spiral-approximation-driven, per the near-Edelbaum thrust-independence of the ratio across 3/5/8 N), a quasi-circular spiral (true for this test's altitude change), and — not exercised here at all — no eclipse/power modeling, no J2, no plane-change component (`Δi=0` reduces the general Edelbaum formula to the simpler `|v₀−v₁|` form used above; the full `√(v₀²+v₁²−2v₀v₁cos(π/2·Δi))` form is unvalidated by this gate and is E3's node-map-pricing concern, not E1's).

## 7z. MISSION_MODEL_V2 §19 E2 — electric propulsion vehicle + event model (568/570/572/440, 2026-07-14)

**Scope: E2 — vehicle model, the LOWTHRUST event kind, and the est./computed accounting lanes. Consumes E1's substrate (§7y) unmodified. E3 (node-map Edelbaum pricing, spiral rendering/LOD, timeline spans) is explicitly deferred.**

**Propellant registry (16f, closed).** `PROG_PROPELLANT_TYPES` (360) gains two entries: `'MMH/NTO'` (storable hypergolic, `boiloff_rate:0`) — registered under the EXACT key 440's `progMakeSpacecraftStageDef`/`progSpacecraftToLiveStages` have always literally emitted (`'MMH/NTO'`, distinct from the UI's own default key `'NTO_A50'`), closing critique 16f without touching any call site — and `'XENON_EP'` (storable, no boiloff; xenon is stored as a supercritical fluid in practice, and this program models no plume/ionization physics).

**Electric-engine fields.** `SpacecraftStageDef` (440) gains `ep_thrust_N`/`ep_isp_s` (undefined by default), shown in the spacecraft editor (580) only when `propType==='XENON_EP'`. `progSpacecraftToLiveStages` carries `propType`/`ep_thrust_N`/`ep_isp_s` onto the LiveStage (previously LiveStages had no `propType` field at all — BURN/LAUNCH never needed it since propellant identity lives on the tank; LOWTHRUST needs it on the STAGE because a stage, not a tank, is what a readiness check is written against, matching how every other per-event capability check in this program reads live-stage fields directly).

**LOWTHRUST vs MNODE (the decision).** A NEW log entry type, not an MNODE mode. MNODE's substrate is built entirely around an impulsive Δv AT A NODE with solve/manual targeting (`_evIsSolvedManeuver`/`_evIsManualBurn`, `progNmComputeEdgeDv`, the node-map from/to geometry) — none of that applies to a burn that spans months and changes the orbit continuously while it happens. Retrofitting LOWTHRUST as an MNODE mode would mean either lying about a from/to node pair for a burn that doesn't target one, or forking half of MNODE's rendering/accounting behind mode checks — a NEW type keeps the two burn philosophies (impulsive/solved vs continuous/est.-then-computed) from cross-contaminating each other's invariants, at the cost of a second `_missionLogCardHTML` branch and a second exec/edit function pair (568/570), which is the smaller price.

**Authored fields** (on the `m.log` entry — authored intent ONLY, per the replay invariant): `duration_s`, `law` ('prograde'|'retrograde'), `throttle` (0-1, scales `ep_thrust_N`). No `coastWindows` in v1 (deferred, per E1 critique 73 — nothing in this pass needed sub-duration on/off scheduling). The acting stage is the vehicle's TOP live stage at that point in the log (`active.stages[length-1]`) — same "active stage" convention as every other capability check in this program; a readiness check (572, id `lowthrust-not-ready`) fails the event with a clear message if that stage's `propType !== 'XENON_EP'` or either engine field is missing/non-positive.

**Est. lane (`ltEstimateLeg`, 568) — always runs, synchronously, inside `missionRecompute`.** Deliberately NOT a full multi-rev Edelbaum spiral integral (that needs the orbit geometry the est. lane doesn't have without a real propagation). Instead: `ṁ = T·throttle/(Isp·g₀)`, `propUsed = min(ṁ·duration, m0−mDry)` (capped exactly like E1's `physMassBurn`), `dv = Isp·g₀·ln(m0/mF)` — the SAME rocket-equation math E1 pinned exactly (§7y "Mass-coupling exactness"), just evaluated once instead of per-integrator-step, because a constant-rate burn's mass ODE is linear in t regardless of how many steps you slice it into. This is exact for "how much prop does this duration burn and what Δv does that buy," which is what the budget/readiness numbers need; it is NOT a claim about the resulting orbit's true (elliptical, precessing) shape — see the next paragraph for that honesty boundary.

**Est-orbit approximation (`ltApplyDvToCircularAlt`, 568) — a documented crude simplification, not a spiral model.** The est. lane needs SOME orbit number to keep the budget/node-map non-blank (spec requirement), so it treats the vehicle's current mean altitude as circular, applies the est. Δv as `v₁ = v_circ(r₀) ± dv`, and back-solves `r₁ = μ/v₁²` via vis-viva for a circular orbit at that new speed. **This is not a spiral** — no eccentricity growth, no multi-rev accounting, no coupling between how the Δv was delivered (continuously, over months) and the resulting orbit shape (which in reality is a slowly-widening near-circular spiral, not a single impulsive raise). It exists purely so `est.`-lane numbers are honest-enough placeholders, exactly parallel to E1's own framing of the est. lane as "cheap and always-on," never conflated with the computed lane's real propagated end state. `estOrbit:true` is stamped on the vehicle's `orbitState` whenever a LOWTHRUST leg is driving it, so any future consumer can tell circular-approximation orbit data from real Kepler/propagated data at a glance.

**Computed lane (`ltComputeTrajectory`, 570) — explicit user action only, chunked, cancellable.** Runs `physPropagateSegment` in 2-day chunks (`CHUNK_S`), carrying `(r,v,m)` forward chunk to chunk via a closure (`_ltRunState`), yielding to `requestAnimationFrame` between chunks so the tab stays responsive and a Cancel button can set `run.cancelled` (checked at the top of the next chunk — a cancel mid-chunk still finishes that chunk, matching the 2-day granularity of the progress bar itself). `opts.singleFrame:true` pins the integration to the vehicle's current body for the whole run — a genuine v1 limit (critique 76 below): a real months-long spiral CAN cross an SOI boundary (e.g. an escape spiral), which this pass does not attempt to patch mid-integration. On completion the result is stored in 568's `_ltComputedByMission[missionId][authIdx]` side-table (a direct sibling of 565's `_physTrajByMission`, same never-on-`m` rule) keyed by the SAME signature the est. lane computes every recompute, then triggers exactly ONE `missionRecompute` so downstream state (budget, orbit, band view) picks up the computed end state — the identical stale-by-one-recompute pattern 570 already uses for physics-TOF duration precedence (critique 32).

**Signature (`ltSignature`, 568, FNV-1a/32 over rounded JSON).** Fields: initial `r`/`v` (mm/mm·s⁻¹-scale rounding — the est. lane's circular-orbit `r,v` proxy, since the est. lane doesn't carry a real Kepler state outside the physics side-table), `m0_kg`, `thrust_N`, `isp_s`, `throttle`, `law`, `duration_s`, `fidelity` (reserved, always `'default'` in v1 — no fidelity toggle wired to this event yet). Recomputed every replay from the CURRENT authored/vehicle-state inputs; compared against the cached record's stored signature. Match → `computed`; mismatch → `stale` (budget/orbit fall back to est., a warn-colored badge shows on the card, 572 emits an info-severity finding); no cached record → `est.`. Not session-persisted BY DESIGN (D6 honesty) — `_ltComputedByMission` is a plain module-global object like `_physTrajByMission`, so a restored session (autosave/.program load) starts with an empty cache and every LOWTHRUST leg renders `stale`-or-`est.` (never a phantom "computed" badge for physics nobody in this session actually ran) until the user clicks Compute again.

**Accounting boundary vs the `progNmComputeEdgeDv` rule (570's hard invariant).** The rule "solved-burn magnitude comes from `progNmComputeEdgeDv`, never recomputed by physics" governs IMPULSIVE MNODE burns, whose whole accounting model is "the edge has one correct Δv, physics either matches it or is wrong." LOWTHRUST has no such edge — there is no impulsive Δv to match, only a continuously-delivered one that is genuinely DIFFERENT depending on which lane priced it (est. rocket-eq vs a real integrated spiral, which loses a few percent to non-impulsive geometry exactly as Edelbaum vs integrated does in §7y's own gate table). So LOWTHRUST is EXPLICITLY exempt from that rule: `e.dv_actual`/`e.prop_consumed` come from whichever lane is active (est. or computed), the prop ledger (`progBurnPropellant`) is fed the SAME number that lane reports (one source at a time, per D6 — never both, never an est.-priced burn with a computed-priced ledger entry), and reconciliation between the two lanes is a DISPLAY concern (the card shows both when they disagree, never silently prefers one) rather than a hard assertion the way `destOnOrbitDV` vs `calculate()` is.

**v2 shadow (566) — NOT wired in this pass (known gap, critique 77).** `v2BuildShadow`'s anchor reconstruction only recognizes LAUNCH/BURN/MNODE/SEPARATE kinds; a LOWTHRUST leg produces no v2 anchor, so `v2StateAt`/`v2DeriveBudget` are blind to low-thrust legs entirely (V1's own `missionBudget`/orbit fields ARE updated, via the recompute case above — this is a V2-shadow-only gap, not a V1 accounting gap). Promoting the computed lane's `stateF` into a v2 anchor (mirroring how a BURN anchor promotes `leg.burnState`+`dvVec`) is the natural follow-on but was out of budget for this pass; documented rather than silently left inconsistent.

**Critiques (new):**
75. **The est-orbit approximation (`ltApplyDvToCircularAlt`) is a single-impulse circular re-solve, not a spiral.** It answers "what circular orbit has the right vis-viva speed after adding this much Δv," not "what orbit does continuously thrusting for N days actually produce" — no eccentricity growth, no coupling to HOW the Δv was delivered over time. Honest for budget-keeping (the Δv/prop numbers ARE the E1-exact rocket-equation values), not for orbit-shape fidelity; the computed lane is the only source of a real end state.
76. **`ltComputeTrajectory`'s chunked integration pins `ctx.center`/`ctx.bodies` to a single body for the whole run (`opts.singleFrame:true`)** — a genuine escape spiral (LEO → C3>0, or a body-to-body low-thrust transfer) would need a mid-run SOI handoff this pass does not attempt; v1's authored use case (raise/lower around one body) doesn't need it, but any future consumer authoring an escape-class LOWTHRUST leg will silently get wrong dynamics past the SOI boundary rather than a frame patch. Flagged, not fixed.
77. **The 566 v2-shadow accounting layer does not recognize LOWTHRUST at all** (see "v2 shadow" above) — `v2StateAt`/`v2DeriveBudget`/`v2Reconcile` are blind to any low-thrust leg's contribution; only V1's own `missionBudget`/vehicle `orbitState` are updated by the LOWTHRUST recompute case. A future pass needs to teach `v2BuildShadow` a `kind:'lowthrust'` anchor (promoting the computed lane's `stateF` when available, the est-orbit circular alt otherwise) before any V2-primary consumer can see these legs.
78. **No coast windows in v1** (spec-deferred, consistent with E1 critique 73): `duration_s` prices/integrates as one continuous burn — a real EP mission with eclipse-driven duty cycling or scheduled off-periods has no representation here.
79. **Samples-cap aliasing is inherited, not newly introduced**: E3 owns spiral/polyline LOD (per-rev vs curvature-adaptive sampling), and this pass does not render a trajectory from the computed samples at all — `physPropagateSegment`'s default `maxSamples:256` decimation would alias badly against a multi-hundred-rev spiral if a renderer naively drew it, which is exactly why E3 is scoped separately. v1 shows only the numeric est./computed ΔV/prop/TOF on the card, no polyline, no schematic dashed-spiral glyph (also E3).

## 7aa. MISSION_MODEL_V2 §19 E3 — Edelbaum pricing math + spiral LOD resampler (568, 2026-07-14)

**Scope: E3 complete — full-form Edelbaum pricing + TOF estimate + rev-boundary resampler (pure math, gate-pinned), WIRED into the node-map dual-pricing tooltip/insert flow (570), the launch-planner escape-spiral line (570/415 consumer), the trajectory-view spiral LOD renderer (574 `_trajLowThrustSVG`), and the timeline-dock span (5747). Browser-verified 2026-07-15 (see the "Wired consumers" section below).**

**Full-form Edelbaum (`ltEdelbaumFullDv`, 568).** `Δv = √(v₀² + v₁² − 2v₀v₁·cos(Δi))`, the law-of-cosines closure between two circular-orbit velocity VECTORS separated by a relative-plane angle `Δi` (input in degrees, clamped to [0°,180°], converted to radians internally). This is the "full form" critique 74 (§7y) flagged as unvalidated by E1's gate — E1 only exercised the `Δi=0` reduction. Interpretation note: the spec text `cos(π/2·Δi)` is read here as "the angle argument IS the plane-change angle in radians" (i.e. `π/2·Δi` with `Δi` itself already expressed as a fraction of a right angle collapses to the same `cos(Δi_rad)` this implementation computes) — documented explicitly because the spec's shorthand admits more than one literal parse; the three closed-form checks below (Δi=0, 90°, 180°) pin the interpretation actually shipped.

Closed-form checks (gate-pinned, "LT E3:" block):
- **Δi=0°** → `cos(0)=1` → `√((v₀−v₁)²) = |v₀−v₁|`, exactly `ltEdelbaumPlanarDv`'s existing planar reduction (bit-identical to 1e-9).
- **Δi=90°** → `cos(90°)=0` → `√(v₀²+v₁²)`, pure quadrature (orthogonal planes — no "cheap" cross term).
- **Δi=180°** → `cos(180°)=−1` → `v₀+v₁`, the full retrograde-relaunch cost (opposite planes — burning INTO the opposing velocity vector).
- **Monotonicity**: cost strictly increases with `Δi` for fixed `v₀,v₁` (0° < 30° < 60° < 90°, all gate-checked) — a physically necessary property (more plane change never gets cheaper) that a broken sign or a wrong angle argument would violate immediately.

Honesty boundary: this is a SINGLE combined-maneuver estimate (the standard textbook Edelbaum circular-to-circular result), not a true multi-rev spiral that optimally distributes the plane-change component across the whole transfer (a real optimal spiral trades altitude-change and plane-change thrust-steering angle continuously; this closed form assumes they're delivered as one lumped velocity triangle). It is an "est." lane number for node-map pricing, exactly parallel to how `ltEdelbaumPlanarDv` was already framed in §7y/§7z — never feeds `progNmComputeEdgeDv`'s impulsive accounting (frozen rule, unchanged).

**TOF estimate (`ltEdelbaumTofEst`, 568).** Given a priced `Δv` (from `ltEdelbaumFullDv` or the planar reduction) and the EP stage's `{thrust_N, isp_s, m0_kg, mDry_kg}`: solves `mF = m0·exp(−Δv/(Isp·g₀))` (same rocket-equation relation `ltEstimateLeg`/E1 pin exactly), then `TOF = Δv / (T/m̄)` with `m̄ = (m0+mF)/2` — a mass-averaged constant-acceleration estimate, consistent with (but coarser than) the est. lane's existing honesty boundary (real accel rises through the burn as mass depletes, §7y). Fails cleanly (`{tof_s:null, mF_kg:null, propUsed_kg:null}`, no NaN/throw) when the priced Δv exceeds what the tank can deliver at that Isp (`mF` would fall below `mDry`) — gate-checked with a 50 km/s dv against a small Xenon tank. Gate also pins: mF/propUsed match the direct rocket-equation values used elsewhere in this module (internal consistency), and doubling thrust halves TOF for the same Δv (accel ∝ T, TOF ∝ 1/accel).

**Rev-boundary resampler (`ltResampleSpiralRevs`, 568) — the spiral-LOD math substrate.** E2 critique 79 flagged that `ltComputeTrajectory`'s samples (near-uniform in TIME, `maxSamples`-capped) alias badly if drawn as a plain polyline through a multi-hundred-rev spiral. This function re-expresses the sample array by ORBITAL REV instead of by time: it unwraps the planar winding angle (`θ = atan2(y,x)`, accumulated across the sequence, sign-aware for either winding direction) to get a continuous "how many revs have elapsed" signal, then splits samples into three buckets — `head` (full per-sample fidelity for the first N revs, default 8), `tail` (same, last N revs), and `mid` (the dense middle decimated to ~1 kept sample per rev boundary crossing). Endpoints are exact (first raw sample always lands in `head`, last always in `tail` — gate-checked). Degenerate inputs (fewer than `head+tail` total revs, <2 samples, or empty) fall back to returning everything in `head` rather than producing an empty/broken split.

Gate validation (synthetic Archimedean spiral, 40 revs × 20 samples/rev = 801 points, `r` growing linearly with angle): recovered rev count matches the constructed 40 revs to within 5% (winding-angle quantization at 20 samples/rev); head/tail each retain ≥90% of their nominal 8-rev×20-samples/rev fidelity; the middle (24 revs) collapses to ≤26 points (~1/rev) rather than 480; total resampled output is under 60% of the raw 801-sample input on this synthetic case (the real win is far larger on the multi-hundred-rev cases E2 flagged — this synthetic case is sized for gate speed, not to showcase the compression ratio).

**Critiques (new):**
80. **`ltEdelbaumFullDv`'s angle-argument interpretation is a documented reading of an ambiguous spec formula, not independently re-derived from an orbital-mechanics reference.** The three closed-form checks (Δi=0/90°/180°) pin internal consistency and monotonicity, which any physically sane implementation must satisfy — but they don't distinguish this interpretation from a different one that ALSO passes those same sanity bounds (e.g. a genuine weighted-Edelbaum formula with a different Δi-to-angle mapping in the 0-180° interior). Anyone wiring this into a real mission-design-grade tool should cross-check the interior values (e.g. Δi=45°) against a second source before trusting the exact numbers, not just the shape.
81. **The full-form Edelbaum estimate prices plane change and altitude change as ONE lumped burn, not the true optimal spiral's continuously-varying steering angle.** A real minimum-Δv Edelbaum spiral front-loads plane change into the high-thrust-efficiency low-altitude portion and tapers it near the end — this closed form is the classical textbook simplification (single velocity-triangle closure), adequate for "roughly how much would this coplanar-ish transfer cost an EP vehicle" node-map budgeting, not a precision low-thrust trajectory optimizer.
82. **The rev-boundary resampler assumes a PLANAR spiral (winding angle computed from x,y only, z ignored).** A real integrated leg with any out-of-plane component (E2 critique 76's un-modeled SOI-crossing case, or any future out-of-plane steering law) would have its winding angle computed against the wrong reference plane — fine for the in-plane raise/lower spirals this pass's LOWTHRUST authoring actually produces (`prograde`/`retrograde` laws only, §7z), a latent trap if `normal`/out-of-plane laws are ever added per §7y's steering-law dispatch note.
83. **This pass's gate validates the resampler against a SYNTHETIC idealized spiral (analytic r(θ)), not against a real `ltComputeTrajectory` output.** The winding-angle-unwrap logic itself doesn't care about the source, but a real integrated trajectory's per-sample angular spacing is irregular (`maxSamples` decimation is time-uniform, not angle-uniform, and a real orbit's angular rate varies with radius even for a near-circular spiral) — the "revCount" recovery accuracy measured here (5% on a clean synthetic case) is a best case, not validated against realistic sample irregularity. (The wired renderer's own browser measurement — 394 revs recovered on a real 30-day integrated LEO spiral, vs the ~470 a naive P(185 km) count predicts — is consistent with the period lengthening as the spiral climbs, not evidence of resampler error; but no independent ground truth for the real case's rev count was computed.)
84. **The envelope annulus HIDES eccentricity pumping and any intra-rev radial structure.** The washer is min/max radius over the ENTIRE decimated middle (one rMin, one rMax) — a spiral whose eccentricity grows mid-transfer (thrust harmonics, resonance crossings, or a future non-tangential law) paints the same smooth band as a perfectly circular climb; per-rev min/max (a radially-graded band or banded rings) would show the pumping but is deliberately out of v1 scope. The middle's ~1 sample/rev decimation also cannot RESOLVE intra-rev structure even if the renderer wanted to draw it — the honesty boundary is "the middle happened somewhere in this radius band over these revs," nothing finer.
85. **The "spiral to escape ≈ v_circ(parking)" launch-planner line is the asymptotic zero-C3 limit, not a mission-specific number.** It prices reaching ESCAPE (C3 = 0) only — the destination's actual departure energy (C3 > 0, from the plan's own Lambert solve shown two lines above it) costs extra Δv this line does not include, and low-thrust trajectories don't cleanly split "escape" from "heliocentric transfer" the way the patched-conic impulsive lane does (a real SEP mission design would optimize the whole heliocentric spiral). The TOF also inherits `ltEdelbaumTofEst`'s mass-averaged constant-acceleration approximation (§7aa above). Labeled est. in the UI; honest as an order-of-magnitude "is EP even viable for this vehicle" readout, which is all the planner line claims.
86. **`e.metStart` is NOT in the computed-leg signature (`ltSignature`), so a computed spiral whose upstream timeline shifts renders at the new MET without going STALE.** The signature covers the physics inputs (r, v, m0, thrust, isp, throttle, law, duration) — editing an EARLIER event's duration slides the LOWTHRUST leg's metStart, and the renderer re-bases the stored burn-relative sample times onto the new metStart (`t: met0 + s.t`). The trajectory GEOMETRY is identical (same initial state, same burn), so V1 accounting stays right, but in a non-inertial N3 frame the per-sample epochs feed the frame transform — a time-shifted replay of the same geometry is genuinely a DIFFERENT frame-relative picture, rendered as if fresh. Same class as critique 71's viewT-snapshot honesty; fixing it means folding metStart into the signature at the cost of spurious STALEs on every upstream timing edit.
87. **Node-map Δi uses inclination difference only — RAAN is ignored** (`_missionLtEdgeEstimate`: Δi = |i₁−i₂|). Two orbits at the same inclination but different Ω have a real relative plane angle up to 2i this pricing charges NOTHING for — the same gap `_nmCoaxialTransferDv` has by default (critique 50), consistent with the builtin nodes not authoring Ω at all. "Coplanar-ish circular orbits" is the spec's own honest scope; `progDvPlaneChangeFull`'s spherical-law-of-cosines angle is the upgrade path if custom nodes with authored Ω ever want real dual pricing.

## Critiques (known weaknesses, roughly by severity)

**Ascent model**
1. K3/K4/T3s/Tmix are fitted empirical constants of unstated provenance and envelope. They validate well against 1960s–present orbital LVs (Saturn V, F9 land within a few % of published capability), but nothing warns the user when a design leaves the fit's envelope (TWR ≪ 1.2 at liftoff, very lofted or depressed trajectories, air-launch).
2. Single static Isp per stage/engine — no altitude dependence. First-stage numbers are whatever the data author blended by hand; two vehicles with identical physics but different Isp-averaging conventions aren't comparable at the few-percent level.
3. The booster integrator blends Isp correctly per interval, but the Townsend penalty is computed from aggregate `A0`/`Isp_avg`/`Ta` — parallel-staged vehicles get a serial-equivalent loss estimate.
4. `Ta`'s fractional-stage interpolation uses an exponential prop-fraction heuristic, not the actual time-to-Vcirc within the stage.

**Destination ΔV**
5. Plane-change logic assumes initial inclination = |site latitude| and charges nothing for inclinations above latitude (real azimuth constraints and range-safety corridors can make those expensive). Retrograde/SSO targets are only "charged" via lost rotation credit.
6. The combined-plane-change-at-apo optimization triggers on an arbitrary `apogee > 10,000 km` threshold; elliptical targets never get the combined treatment (plane change added scalar, not vectorially).
7. Tolerance constants (5 km "circular", 50 km "same perigee", 0.5° plane-change deadband) are unlabeled magic numbers.
8. Escape declination penalty is a crude great-circle plane change at parking speed; no DLA/azimuth interaction.

**S1.5**
9. BECO located on stage-only mass (payload ignored) — the "< 5 %" error claim is asserted, not tested, outside Atlas-class proportions.
10. Phase-1 blend (when used) is static; booster-pack jettison is instantaneous with no thrust decay, and `s15_beco_twr` defaults to 1.2 regardless of vehicle.
10a. The blend's sustainer term uses `s15_sust_isp`, which the library stores as the VACUUM value (it primarily serves Phase 2) — so the Phase-1 blend is optimistic at low altitude, where the sustainer's real SL Isp is far worse (LR-105: ~215 s SL vs 309 s vac). With Atlas data the blend RAISED Ph.1 Isp (282 → 285.5 s) rather than lowering it. To make the blend represent liftoff conditions you'd need a separate sea-level sustainer Isp field, or the user must fold the pessimism into `s15_boost_isp`. Known and accepted for now.

**Mission / node map**
11. Two ascent models coexist: Townsend (when LV performance data exists) vs `Vcirc + fixed-loss table`. A mission can silently switch fidelity depending on how the vehicle was created. The loss table itself (Earth 1550 etc.) is a rough constant independent of TWR or target altitude.
12. LOI/TEI patched-conic underestimates (~10 %, documented); TEI = LOI symmetry is a simplification; no free-return or finite-burn losses anywhere.
13. Interplanetary transfers: circular coplanar planets, no plane change, no arrival-timing coupling between the node map ΔVs and the porkchop's Lambert solutions — the two subsystems can disagree about the same trip.
14. Docking tolerance windows (1 km, 0.1°, 1° LAN) are arbitrary, and `epoch`/phasing is entirely ignored — co-orbital ≠ co-located.
15. Lunar/Mars ascent = scaled constants; no TWR sensitivity, no plane targeting from launch site latitude on those bodies.
16. Boiloff: constant fractional rate, insulation as a linear multiplier in the exponent; no tank thermal state, no ullage/pressurization losses. Rate is constant over the whole coast regardless of duration — a 261-day cislunar loiter and a 3-day one lose mass on the exact same exponential curve, with no allowance for a tank's fill fraction changing its effective surface-to-volume ratio over time.
16f. Propellant-type provenance is asymmetric and easy to get wrong silently: launch-vehicle stages always get a valid cryo/storable type (Isp-inferred by `progVehicleDefToLiveStages`), so they DO boil off; spacecraft stage definitions default to `propType: 'MMH/NTO'`, which is not a registered key in `PROG_PROPELLANT_TYPES` — an unedited spacecraft stage therefore boils off NOTHING, not because MMH/NTO is storable (it correctly would be, if modeled) but because the lookup silently misses. The net effect (storable-by-default) happens to be physically reasonable for a real MMH/NTO service module, but it's an accident of naming, not a deliberate default — a future propellant type added to the registry under a different key would need to also update this default, and nothing enforces the two stay in sync.
16g. Boiloff during LAUNCH ascent is modeled (applied, not skipped) but negligible by construction — ascent burn times are minutes, and the exponential over minutes is indistinguishable from zero at any realistic cryo rate. Documented rather than special-cased to avoid a silent gap in the "every clock advance boils off" invariant.

**Mission time (T1)**
16a. Hohmann-model TOF ≠ real trajectories: the translunar half-ellipse estimate lands ~5 days vs. Apollo's actual ~3-day free-return trajectory — the model doesn't know about faster non-Hohmann transfers, and overrides are the intended escape hatch for any mission that needs an accurate date.
16b. All burns (BURN and MANEUVER) are treated as impulsive/instantaneous in the clock — only the COAST/transfer between them accumulates time. A long low-thrust burn would in reality itself take meaningful time; not modeled.
16c. Interplanetary TOF ignores launch-window phasing (planets aren't actually where a Hohmann departure needs them) unless the mission has a specific porkchop-selected Lambert window (`PROG_ACTIVE_PROGRAM.launchWindow`) — absent that, the number is a generic Hohmann estimate, not a real date.
16d. `durationOverride`/`dvOverride` intentionally bypass the physics by design — they exist so the user can substitute a known real value (e.g. actual Apollo TOF/ΔV) for the model's estimate. The UI badges overridden events "(custom)" so this is never silently confused with the computed value, but nothing prevents an override that's physically inconsistent with the vehicle's actual propellant/ΔV budget beyond the normal margin checks.
16e. Transit-corridor convention: a coast is charged once, on the leg EXITING the corridor node (TLC→LLO carries the ~5 d translunar TOF; LEO→TLC is the impulsive injection, 0 s). Found the hard way: the first implementation charged both legs and doubled every corridor transit.

**Boiloff on clock advancement (T2)**
16h. Boiloff is applied to EVERY live vehicle whenever ANY vehicle's clock-advancing event fires — a docked depot idling in LEO boils off in step with the vehicle actually coasting to the Moon, which is physically correct (time passes for everyone), but it means a mission with many idle vehicles pays the boiloff cost once per clock-advancing event rather than once per vehicle-day, which is the same total mass loss but a different (equivalent) computational path worth noting for anyone auditing `applyMissionBoiloff` in `missionRecompute` (570).
16i. The readiness check's cumulative-boiloff percentage (572, `boiloff-losses`) divides by "initial propellant capacity," which is captured at LAUNCH/DEPLOY time (`fv._initialPropCap`). A vehicle born mid-mission from a SEPARATE or DOCK (no LAUNCH/DEPLOY of its own) has no cached initial value; the check falls back to that vehicle's CURRENT capacity at the moment boiloff is first detected, which understates the percentage for any vehicle whose stages were combined after already losing propellant to burns — a known, documented approximation, not a hard guarantee.

**Body kinematics (C1a) — RETIRED BY R1 (2026-07-09)**
16j. ~~No ephemeris~~ — RESOLVED: R1 rails are the JPL approximate mean elements evaluated at real absolute time (`epochJD`); `t=0` is a calendar date.
16k. ~~Perfectly circular orbits~~ — RESOLVED: real eccentricities (Mercury e=0.2056, Moon e=0.0549) with elliptical speed variation (analytic Ė-form velocity).
16l. ~~Everything coplanar~~ — RESOLVED: bodies have real inclinations and 3D states (R1), the renderer is a 3D camera over true geometry (R2), and vessel states carry their authored inclination (R3, §7h). Remaining plane fictions are the Ω=0 convention (critique 49) and the schematic plane-change accounting (critique 50).

**Trade studies**
17. Inclination/altitude sweeps use the minimal circular-orbit ΔV replica (clearly labeled) — fine for trends, not for elliptical or escape comparisons.
18. Tornado is one-at-a-time and symmetric: no parameter interactions, no asymmetric sensitivities (e.g. Isp loss usually hurts more than gain helps near margin limits).

**Trajectory view LOD + mission-state rendering (C2)**
21. Vehicle-on-arc position (`_trajArcPointAt` driven by `_trajLegPathFraction`) is uniform PATH-LENGTH-ANGLE progress along the drawn half-ellipse, not true orbital motion — real vehicles move faster near periapsis (non-uniform true-anomaly rate under Kepler's second law), so the dot's on-screen speed is constant while a real vehicle's isn't. Schematic "roughly here" indicator only. — **Retired for physics-backed legs (P3, 2026-07-09)**: legs with a propagated side-table record place the dot by interpolating the propagated samples at viewTime (`_trajPolylinePointAt`, §7f), which IS Kepler-true to sample resolution; the linear-fraction schematic remains only for legs without physics (physics off, degenerate/unpropagated legs).
22. The Moon-frame patched-conic seam fallback (`_trajLocalRadius`'s `max(2×bodyR, 0.5×mo.r)` departure radius for a transit arriving at its own destination frame) is an arbitrary rendering placeholder, not a Hill-sphere/SOI calculation — it exists purely so the arc has SOME finite departure point to draw from in the destination's own frame; the radius value carries no physical meaning (it's tuned to clear the transferArc LOD window's px floor across camera anchors, not to model the real hyperbolic approach geometry).

64. **Solve method (converged form, 2026-07-14):** (i) **perilune quantization** — arrival epochs are restricted to the NRHO's perilune crossings (tArr ≡ tPeri mod period, within a 2.5-7.3 d coast band; the perilune point sits only ~3,000 km from the Moon's center, physically reachable by a TLI-class departure — see critique 65's history for why a free-floating TOF failed); (ii) closed-form RAAN solve per candidate epoch, aimed at the **target sample's own Earth-frame direction** (Stage-1 fix; near-degenerate with the Moon-center direction at perilune but exact); (iii) coarse 24-point θ grid across all candidate epochs x Ω roots + two-level local θ refinement, scored by the full 3D miss to the FIXED target point; (iv) 2-DOF Newton (`physShootToTarget`, θ + in-plane pitch, fixed arrival epoch, in-plane [x,y] Moon-frame miss), with a 3-DOF [θ, pitch, yaw] escalation kept only if it improves; (v) **Stage-2 mid-course correction**: if the fixed-|Δv| TLI still misses the 2,000 km window, a free small MCC Δv vector at tMcc = TLI + 0.5·TOF is solved by 3-DOF Newton against the target position at the fixed arrival epoch — a near-linear problem (small Δv, multi-day lever arm) that converges in a few iterations. The MCC is a solver-authored burn (like `physFreeReturnSolve`'s — its magnitude is genuinely free); the TLI's accounted |Δv| stays byte-identical to the engine value throughout. **MISSION_MODEL_V2 §17 N3 — switchable reference frames (§7x, 574/425, 2026-07-14)**
70. **`body-fixed` frame only freezes the ANCHOR body's own surface features — it does not re-express other bodies'/markers' apparent sky motion due to that body's spin.** A true planetographic view (as seen from a fixed point on a rotating body) would show the Moon and other bodies sweep across the sky once per rotation period; this renderer's `body-fixed` frame only cancels the spin baked into the anchor's OWN globe texture/site markers (§7x seam (d)) — other bodies still render at their raw `viewT` position (seam (c)), unaffected by the anchor's spin. Extending this would mean threading `t=viewT` through `_trajFrameTransform('body-fixed', anchorBody, ...)` for every OTHER body's glyph too — geometrically straightforward (the formula already supports it) but deliberately out of scope for N3 (the agreed use case was "launch-site work", i.e. freezing the ground track, not a full planetographic sky view). Documented, not hidden.
71. **The heliocentric/moon Keplerian reference rings (`trueRingPath`, analytic `progOrbitSamplePoints`) render at a single `viewT` snapshot regardless of frame** — they have no per-point epoch to thread through the transform (an osculating ellipse is evaluated at one epoch by construction), so in a rotating frame they show that ellipse's shape rotated into the frame's orientation AT VIEWT, not a truly time-varying frame-relative shape. This is consistent (every other body glyph is also a viewT snapshot, seam (c)) but is a coarser treatment than the propagated-orbit rings (seam (b)), which genuinely close live from real per-sample epochs. No consumer currently needs a frame-relative Keplerian ellipse to be more than a viewT snapshot; flagged for whoever eventually does.
